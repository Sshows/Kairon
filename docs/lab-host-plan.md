# План лабораторного сервера: ещё не развёрнут

Пользователь подтвердил, что VPS пока нет. На Этапе 0 готовится проект конфигурации; контейнеры не запускаются. Исполняемый Compose будет добавлен на Этапе 3 после выбора сервера и проверки модели изоляции.

## Состав VPS

- Поддерживаемый Linux, Docker Engine/Compose, reverse proxy с HTTPS, отдельный терминальный шлюз.
- Orchestrator в доверенной управляющей сети. Доступ к Docker API только у него, без передачи сокета учебным контейнерам. Компрометация orchestrator означает риск для хоста; для него нужен отдельный сервисный контур.
- Каждый запуск создаёт новую сессионную сеть и новые Kali/target контейнеры. Образы фиксируются по digest после проверки и собираются до начала занятия.
- Доверенная проверка располагается вне управляемой учеником файловой системы. Сервер выбирает команды по утверждённому template ID; произвольная команда из браузера или MCP не становится командой хоста.
- Ollama получает модели заранее. В рабочей сессии внешние загрузки и облачные fallbacks выключены. Если модель недоступна, интерфейс обозначает симуляцию либо ошибку инфраструктуры.

## Обязательные свойства будущей конфигурации

`internal: true`, отсутствие опубликованных портов целей, `cap_drop: ALL`, `no-new-privileges`, непривилегированный UID, `read_only` там, где совместимо; отдельные временные writable volumes/tmpfs; никакого host network, host PID, устройств, Docker socket, host bind mounts или privileged. Исключения под инструмент Kali принимаются по конкретному уроку после проверки; широкие привилегии не выдаются «на всякий случай».

Лимиты памяти/CPU/PID/времени и число одновременных сессий задаются в шаблоне. Orchestrator проверяет фактические Docker limits после создания. Конкретные размеры выбираются по измерениям образов и числу учащихся, а не по неподтверждённой оценке RAM. Сессию прекращают по TTL, простою, блокировке аккаунта и ручной остановке. После рестарта сервис сверяет сохранённые сессии с Docker и удаляет осиротевшие ресурсы.

**Одна внутренняя Docker-сеть не блокирует хост.** [Документация Docker](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal) допускает доступ к gateway и доступным сервисам хоста. Понадобятся отдельные правила host firewall/nftables для INPUT и FORWARD, ограничения metadata/link-local/private management ranges и проверка и IPv4, и IPv6. Разрешения терминального шлюза и checker задаются явно. Правила должны переживать рестарт Docker и проверяться на целевом VPS. Готовые непроверенные firewall-команды в этот этап не включаются.

## Приёмка Этапа 3

1. Учебная машина не достигает Интернета, host gateway/service, metadata endpoint и управляющей сети.
2. Сессия А не видит и не меняет контейнеры/данные сессии Б. Чужой WebSocket token отклоняется; Origin проверяется; токены короткоживущие и привязаны к владельцу.
3. Из браузера доступны только авторизованные терминал/прокси своей цели. Порт уязвимой цели не открыт миру.
4. Исчерпание CPU/RAM/PID остаётся внутри сессии; TTL/idle cleanup работает после переподключения и рестарта сервиса.
5. Обязательные проверки нельзя изменить учеником; skipped/timeout/error не превращаются в pass.
6. Нагрузочная проверка определяет вместимость VPS. Резервирование ресурсов не даёт одному ученику остановить другие сессии.

Для заданий по ядру, выходу из контейнера или широкому повышению привилегий потребуется отдельный VM/microVM-пул. GOAD — Windows VM-стенд и не входит в обещание «все лабы — Linux Docker». До появления соответствующей среды такие задания не публикуются.
