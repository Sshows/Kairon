# Вход, роли и данные пользователей

Auth.js 5 beta Credentials используется по исходному ТЗ. Это зафиксированная beta-зависимость, которую нужно обновлять осознанно с повторением проверок. Открытого signup, демо-аккаунта и пароля по умолчанию нет.

При входе Zod нормализует email и проверяет длину. bcrypt использует cost 12 и не принимает пароли длиннее 72 байт. Для неизвестного email выполняется сравнение с фиктивным хешем, не связанным с аккаунтом. Прежде чем выполнять bcrypt, сервер атомарно списывает попытку через PostgreSQL: до 8 попыток за 15 минут на HMAC email. Это общий лимит для экземпляров Vercel. Лимит по IP/периметру и защита от распределённой нагрузки требуют отдельной настройки на этапе 7.

JWT хранится средствами Auth.js в защищённой сессионной cookie; максимальная длительность 8 часов. На каждом запросе к защищённой странице/API сервер читает актуальную запись пользователя и проверяет blocked/sessionVersion. Роль из формы или клиентского хранилища не используется. ADMIN проверяется отдельно; скрытая ссылка в меню не является защитой. CSRF для входа/выхода обеспечивает Auth.js, Server Actions проверяют происхождение запроса средствами Next.js.

## Роли БД

- Владелец по DIRECT_URL: миграции и локальный админский CLI. Не используется в веб-runtime.
- `kairon_runtime`: LOGIN, без superuser/BYPASSRLS/CREATEROLE/CREATEDB, без членства в других ролях. Может читать свою User-строку, менять только собственное согласие/updatedAt, читать/добавлять свой аудит и вызывать две узкие функции входа.
- `kairon_auth`: NOLOGIN; владеет SECURITY DEFINER-функциями, читает User и ведёт LoginAttempt. Не владеет таблицами. PUBLIC лишён EXECUTE этих функций. Search path фиксирован в pg_catalog, таблицы указаны с public.

FORCE RLS включён на User/AuditLog/LoginAttempt. Приложение проверяет полномочия runtime при первом доступе. `withUser` устанавливает `app.user_id` через параметризованный `set_config(..., true)` внутри транзакции. После COMMIT/ROLLBACK значение очищается, что важно для pooled Neon. Только проверенная серверная сессия выбирает userId; HTTP-поле/X-Tenant-Id не является источником полномочий.

Это защита от пропущенного пользовательского фильтра в доверенном серверном коде. Runtime-DSN является секретом: обладатель прямого SQL-доступа способен задавать custom settings; RLS с общим сервисным подключением не делает такой доступ безопасным для конечных пользователей. Приложение не принимает произвольный SQL и не выдаёт runtime-DSN лабораториям или MCP-клиентам.

Учебный прогресс ещё не создан. При добавлении Progress/Attempt/XP/LabSession на следующем этапе требуется такая же политика владельца, FORCE RLS и реальные тесты чужих строк. Нельзя объявлять будущий Progress защищённым только по этой текущей миграции.

## Секреты и эксплуатация

`.env.local`, `.vercel`, сгенерированный Prisma client и следы тестов не коммитятся. Отладочный вывод драйвера/DSN не включён в auth logger. Публичный `/api/health` сообщает живость веб-процесса, а не готовность БД/лабораторий.

У аккаунтов пока нет самостоятельного восстановления/смены пароля, MFA и веб-редактора. Согласие правил сохраняется с action `ETHICS_ACCEPTED_V1`; при изменении правил понадобится отдельная версия принятия. Ни текст страницы правил, ни эта техническая инструкция не заменяют юридические документы для выбранной юрисдикции и оператора платформы.

Официальные источники: [Auth.js Credentials](https://authjs.dev/getting-started/authentication/credentials), [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [Prisma/PostgreSQL](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/postgresql).
