# Аккаунты, Gmail и личный прогресс — версия 0.14

Все уроки остаются бесплатными. Без входа можно читать материалы, скачивать
наборы и проходить самопроверки. Аккаунт нужен для сохранения между устройствами.

## Как это выглядит для ученика

1. Нажать «Войти» → «Создать аккаунт». Указать свою почту, имя и новый пароль
   **для Kairon**, а не пароль от почтового ящика. Минимум 12 символов;
   ограничение bcrypt — 72 байта, поэтому длинный русский пароль может
   занимать больше места, чем такое же число латинских букв.
2. Получить письмо и ввести 6 цифр. Письмо действует 10 минут; после пяти
   неверных попыток нужен новый код. До подтверждения аккаунт не создаётся.
3. Войти с почтой и паролем. Правильная самопроверка сохраняет отметку урока.
   На странице дня можно самостоятельно поставить «Я закончил день».
4. В нужном дне или уроке открыть «Сохранить место и заметку», написать,
   например, «Остановился перед шагом 3», и нажать «Сохранить место».
   На главной и в плане появится «Вернуться к закладке».
5. На другом устройстве войти с той же почтой. Отметки, закладка и заметка
   загрузятся из Neon. После выхода они останутся в базе.

В аккаунте одна закладка: новая заменяет прежнюю. Это явно написано перед
сохранением. Отметки самопроверок и личные отметки дней учитываются отдельно.
День в общем плане считается завершённым, когда отмечен вручную либо пройдены
все его самопроверки. Снятие личной галочки не удаляет результаты самопроверок.

Старые гостевые отметки не импортируются автоматически. В «Моём прогрессе»
показано их количество и кнопка «Это мои отметки — перенести». Это важно для
общего компьютера. Импорт добавляет известные ID к аккаунту, сохраняет уже
имеющиеся результаты и затем очищает гостевые отметки в этом браузере.

Если сервер не подтвердил запись, интерфейс сообщает об ошибке. После
правильного ответа можно повторить сохранение. Приложение не показывает
«сохранено в аккаунте» только на основании изменения состояния браузера.

## Реальный набор технологий

| Часть | Технология | Задача |
| --- | --- | --- |
| Интерфейс | Next.js, React, TypeScript, CSS | Уроки, формы, личные отметки |
| Сервер | Next.js Route Handlers на Node.js, Vercel | Проверка кода, вход, запись прогресса |
| Вход | Auth.js Credentials, bcrypt | Сессия в HttpOnly cookie, проверка хеша пароля |
| Данные | PostgreSQL в Neon, Prisma с pg adapter | Аккаунты, коды, отметки, закладки |
| Почта | Nodemailer, Gmail SMTP с TLS | Служебные коды регистрации и восстановления |
| Исходники и проверки | GitHub, GitHub Actions | Код, миграции, инструкции, автоматические проверки |

Kairon уже использовал Next.js и React, поэтому он не переписан в три файла
`index.html`, `style.css`, `script.js`. Серверный код находится в `src/app/api/`
и `src/lib/`. React используется; PHP и Python не используются для авторизации
сайта. Python-файлы в учебных наборах предназначены для практики учеников.

## Neon: одна база, отдельные строки каждого пользователя

Не требуется отдельная PostgreSQL-база для каждого человека. У аккаунта есть
уникальный `User.id`. Связанные строки содержат `userId`:

- `User`: почта, имя, хеш пароля, подтверждение, служебная версия сессии.
- `EmailChallenge`: временный HMAC кода, назначение, срок, число попыток;
  для регистрации — будущие имя и хеш пароля. Сам код в базу не попадает.
- `LessonProgress`: пройденные самопроверки; старые записи сохранены.
- `StudyDayProgress`: личные отметки дней, уникальная пара `(userId, day)`.
- `StudyBookmark`: одна закладка и заметка, первичный ключ `userId`.
- `LoginAttempt`: общие для всех серверных функций счётчики ограничений.

Сервер берёт `userId` из проверенной сессии. `accountId` в запросе лишь
проверяет, что старая вкладка не пытается записать данные после смены аккаунта;
при несовпадении запрос получает 409. Подмена этого поля не даёт доступ к
чужим данным. Дополнительно PostgreSQL применяет FORCE RLS.

Миграция `202610310001_personal_learning` добавляет таблицы и поле
`emailVerifiedAt`; не удаляет пользователей, роли или историю. Старые аккаунты
без подтверждения почты используют «Забыли пароль?»: подтверждение через
почту сохраняет прежний ID и прогресс, устанавливает новый пароль и отзывает
старые сессии. Пароли от ранее созданных аккаунтов не пересылаются.

## Gmail и Vercel

Дополнительный сервер Render не требуется. Используются существующие Neon и
Vercel. Платные сервисы в этой реализации не подключены. Бесплатные планы и
личный Gmail имеют ограничения; это решение для небольшого учебного сайта.
В коде установлен предел 180 запросов писем в сутки на отправителя, а также
ограничения на почту и адрес запроса. Это защита от расходования квоты,
не обещание гарантированной почтовой доставки или неограниченной нагрузки.

Production-переменные Vercel:

| Имя | Значение / назначение |
| --- | --- |
| `DATABASE_URL` | Pooled Neon URL ограниченной роли `kairon_runtime` |
| `AUTH_SECRET` | Случайный серверный секрет от 32 символов |
| `SMTP_USER` | Адрес Gmail отправителя |
| `SMTP_PASSWORD` | Отдельный 16-значный пароль приложения Google |

`DIRECT_URL` владельца используется только для миграций и обслуживания,
не добавляется в Vercel runtime. Секреты не имеют префикса `NEXT_PUBLIC_`,
не коммитятся и не возвращаются через API. Обычный пароль Google не нужен.

Для Google требуется включённая двухэтапная проверка и отдельный пароль
приложения «Kairon» в [настройках Google](https://myaccount.google.com/apppasswords).
Правила и доступность: [справка Google](https://support.google.com/accounts/answer/185833).
Пароль приложения сохраняется напрямую в Production-переменную Vercel.
После изменения переменных требуется новый deployment. При смене пароля
Google пароли приложений отзываются: нужно создать новый и обновить секрет.

Сервер использует `smtp.gmail.com:465` с TLS и проверкой сертификата. `from`
всегда совпадает с `SMTP_USER`; пользователь не может подменить отправителя,
тему или текст. Письмо содержит только код, его назначение и инструкцию.
[Nodemailer: Gmail](https://nodemailer.com/usage/using-gmail/).

Nodemailer закреплён на 10.3.1 через npm override: Auth.js beta декларирует
более старый optional peer для своего email-провайдера. Здесь этот провайдер
не используется: Auth.js отвечает за Credentials, отправку выполняет свой
фиксированный транспорт. Совместимость проверяется сборкой и полным входом.

## Разработка и проверки

1. `npm ci`.
2. Создать `.env.local` на основе `.env.example`. Для разработки использовать
   отдельную ветку/базу Neon, не production. Указать `DIRECT_URL` владельца.
3. `npm run db:migrate`, затем при первом создании роли `npm run db:provision`.
   Последний скрипт отказывается заменять уже существующий `DATABASE_URL`.
4. Указать `AUTH_SECRET`, `AUTH_URL=http://localhost:3000`,
   `AUTH_TRUST_HOST=true`. Для локальных тестов — `KAIRON_TEST_MAIL=1`.
   Этот режим работает только вне Vercel с указанным localhost URL.
5. `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:accounts`,
   `npm run build`, `npm run test:e2e`.

Playwright сам запускает локальный тестовый SMTP на 127.0.0.1:2526 и
вспомогательный почтовый HTTP на 127.0.0.1:8026. Письма не уходят наружу.
Это отдельный скрипт тестирования, а не публичный API чтения кодов.
В CI используется временный PostgreSQL с тестовыми паролями, без секретов Neon
и Gmail. Проверяются два человека на днях 20 и 46, второе устройство, перенос
гостевых отметок, восстановление, отзыв сессии и защита чужих строк в БД.

Для production миграции выполняются владельцем после успешной проверки на
тестовой базе. Не применять `prisma migrate reset` к рабочей базе.
Подробности защиты — [auth-security.md](auth-security.md).
