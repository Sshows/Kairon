## Кто ты и к какому объекту просишь доступ

При входе сайт выясняет, кто перед ним: это аутентификация. Когда пользователь просит конкретный заказ, сервер должен решить, можно ли **этому пользователю выполнить это действие с этим заказом**: это авторизация. Одно успешное решение не заменяет другое. Наличие действующей сессии означает «мы узнали пользователя», а не «ему разрешено всё».

Сравни с гостиницей. Администратор проверил паспорт и выдал ключ от твоего номера. Теперь ты зарегистрированный гость. Это не даёт права забрать ключ от любого соседнего номера. Номер комнаты помогает найти дверь, но не определяет, кому её можно открыть. Так же устроен идентификатор заказа в URL.

В главе 16 Real-World Bug Hunting рассматриваются и последовательные номера, и случайные идентификаторы. Случайный UUID усложняет угадывание, однако сервер всё равно должен проверять право доступа. В некоторых продуктах случайная ссылка намеренно является способом общего доступа; тогда необходимо учитывать именно эту модель продукта. В нашей практике правило однозначно: заказы приватны и видны только владельцу.

## Подготовь две личности и два объекта

Начнём без HTTP-сервера, чтобы полностью увидеть ошибку в обработчике. Открой терминал Kali:

```bash
mkdir -p ~/kairon-reading/access
cd ~/kairon-reading/access
```

`~` означает твою домашнюю папку. В Mousepad создай здесь файл `access_demo.py`. Вставь код целиком, сохраняя отступы:

```python
orders = {
    101: {"owner": "anna", "note": "TEST-A-ONLY"},
    202: {"owner": "boris", "note": "TEST-B-ONLY"},
}

def vulnerable(current_user, order_id):
    if not current_user:
        return 401, None
    order = orders.get(order_id)
    if order is None:
        return 404, None
    return 200, order

def protected(current_user, order_id):
    if not current_user:
        return 401, None
    order = orders.get(order_id)
    if order is None or order["owner"] != current_user:
        return 404, None
    return 200, order

cases = [("anna", 101), ("boris", 202), ("anna", 202), (None, 101)]
for user, order_id in cases:
    print("user=", user, "order=", order_id)
    print("before:", vulnerable(user, order_id))
    print("after: ", protected(user, order_id))
```

`orders` — учебная база в памяти. Ключи `101` и `202` обозначают объекты, а поле `owner` хранит владельца. Маркеры `TEST-A-ONLY` и `TEST-B-ONLY` позволяют узнать содержимое, которое по правилам должно оставаться приватным.

`current_user` моделирует личность, уже установленную доверенной сессией. В настоящем обработчике нельзя просто взять её из изменяемого клиентом поля `user=anna`. Здесь параметр передаёт наш проверяющий код, чтобы наглядно показать все варианты. Возвращаемые числа похожи на HTTP-статусы, но программа не отправляет сетевые запросы: это модель серверной проверки, которую мы видим изнутри.

## Найди ошибку по порядку действий

Первая функция сначала требует присутствия пользователя, потом находит заказ. На этом проверка заканчивается. Прочти код обычными словами: «Пользователь вошёл? Заказ существует? Тогда отдать». В этой фразе нет главного условия — принадлежит ли заказ этому пользователю.

`orders.get(order_id)` возвращает запись либо `None`, если номера нет. Проверка `if order is None` отсекает неизвестные объекты. Она полезна, но отвечает только на вопрос существования. Если запись существует, первая функция возвращает её любому вошедшему пользователю.

Вторая функция добавляет сравнение `order["owner"] != current_user`. Знак `!=` означает «не равно». Если запись отсутствует **или** принадлежит другому человеку, возвращается отказ без содержимого. Для обоих случаев здесь выбран `404`, чтобы не различать чужой и несуществующий заказ. В другом приложении допустим `403`: важно само решение доступа и отсутствие приватного тела, а не одна обязательная цифра для всех систем.

Запусти:

```bash
python3 access_demo.py
```

В случае `anna, 101` обе функции должны вернуть данные Анны. В случае `boris, 202` обе вернут данные Бориса. В случае `anna, 202` ошибочная функция покажет `TEST-B-ONLY`, а исправленная — `(404, None)`. Для `None, 101` обе вернут `(401, None)`: незнакомый пользователь не получает заказ даже в первой версии.

Разрешённые случаи остались рабочими. Именно поэтому нельзя считать исправлением простой запрет всех запросов. Защита должна выполнять правило продукта, а не просто показывать ошибку каждому посетителю.

## Перенеси рассуждение на настоящее приложение

В HTTP-версии `order_id` может приходить из `/orders/202`, поля JSON или вложенного параметра. Источник формы не меняет правило. Сервер получает пользователя из сессии и находит разрешённый объект, например условием `id = нужный_номер AND owner_id = пользователь_сессии`. Это логическое условие; параметры SQL передают через безопасный механизм драйвера, а не склеивают с пользовательскими строками.

Открывая два аккаунта в браузере, используй разные профили или обычное и приватное окно. Две вкладки одного профиля обычно делят cookie: вход во второй вкладке может поменять личность первой. Тогда ты будешь думать, что проверяешь А, хотя запрос уже отправляет Б. Сначала проверь собственный объект каждого аккаунта и только после этого делай перекрёстный запрос.

Сравнивай не только статус, но и значимые поля ответа. Сервер может вернуть `200` со строкой `access denied`; это не чтение чужого заказа. И наоборот, запретный статус с приватными данными в теле всё ещё может раскрывать информацию. Для доказательства запиши, какая личность отправила запрос, какой объект ожидался и какое приватное поле фактически пришло.

## Проверь исправление шире одного номера

Добавь в `cases` вариант `("boris", 101)` и неизвестный заказ `("anna", 999)`. Борис не должен читать заказ Анны, неизвестный заказ тоже недоступен. Добавь второй заказ Анны, например `303`: собственный новый объект должен оставаться доступным. Так проверяется само правило, а не исключение специально для номера 202.

Если продукт использует организации и роли, модель сложнее. Владельцем может быть команда, а пользователю разрешён просмотр только в одной организации. Тогда условие должно учитывать членство, роль, действие и состояние объекта. Проверка чтения не доказывает, что изменение и удаление проверяются тем же способом: эти обработчики тоже требуют своих проверок.

Типичная ошибка начинающего — спрятать кнопку в интерфейсе и считать доступ закрытым. Кнопка помогает пользователю, но запрос можно отправить независимо от неё. Другая ошибка — заменить номера на UUID и забыть о серверном решении. Третья — проверить только положительный случай, когда всё принадлежит одному аккаунту.

Запиши итог отчёта: «В исходной модели Анна получила приватный заказ Бориса. Причина — после поиска записи отсутствует сравнение владельца с доверенной личностью. После исправления собственные заказы доступны, перекрёстные запросы отклоняются». Теперь ты можешь объяснить и саму ошибку, и место исправления, и способ проверить результат без громких обещаний о “полном взломе”.
