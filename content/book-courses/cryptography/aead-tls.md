## Перед началом: Шифровать и проверять подлинность — разные действия

Представь закрытую посылку. Замок скрывает содержимое от того, у кого нет ключа. Но получателю также важно узнать, не изменили ли посылку в пути и относится ли видимая наклейка именно к этому содержимому. В цифровой системе нужны ясные свойства: конфиденциальность, целостность и подлинность в выбранной модели ключей.

Одного факта «получился нечитаемый текст» недостаточно. Некоторые способы шифрования допускают предсказуемые изменения расшифрованных данных при изменении шифротекста. Поэтому приложения используют проверенные конструкции аутентифицированного шифрования. В главе 8 Serious Cryptography сначала сравниваются способы сочетания шифра и MAC, затем вводится AEAD — шифрование с аутентификацией дополнительных открытых данных.

Мы воспользуемся AES-GCM из готовой библиотеки. AES — блочный шифр, GCM — режим его применения, объединяющий шифрование и аутентификацию. Нам не нужно вручную реализовывать операции AES или GHASH, чтобы понять интерфейс и обязательства приложения. Нужно точно знать, какие значения передаются и что делать при ошибке проверки.

## Почему это работает: Четыре входа и один проверяемый результат

**Ключ** — секрет между сторонами. В примере он случайный и существует только во время работы программы. **Nonce** — значение для конкретной операции шифрования. Для данного ключа в GCM его нельзя повторять. Он не обязан быть секретным, но его уникальность критична: повтор способен разрушить свойства режима.

**Открытый текст** — сообщение, которое нужно скрыть. **AAD** — дополнительные данные, которые остаются видимыми, но должны участвовать в проверке. Например, номер заказа можно оставить на наклейке для маршрутизации, одновременно связав его с зашифрованной суммой. Если изменить номер, проверка должна провалиться.

При шифровании получаются шифротекст и проверочная метка, tag. В интерфейсе `AESGCM.encrypt` библиотеки `cryptography` метка добавляется к возвращённой последовательности байтов. Для расшифрования нужны тот же ключ, правильный nonce, AAD и полная возвращённая последовательность. Подмена любого из этих входов должна приводить к отказу проверки.

## Сделай сейчас: Подготовь библиотеку в Kali

Открой терминал Kali. Для системного Python можно установить пакет из репозитория дистрибутива:

```bash
sudo apt update
sudo apt install python3-cryptography
mkdir -p ~/kairon-reading/crypto
cd ~/kairon-reading/crypto
python3 -c "from cryptography.hazmat.primitives.ciphers.aead import AESGCM; print('AESGCM ready')"
```

`apt update` обновляет список доступных пакетов, а `apt install` устанавливает библиотеку. `sudo` относится к установке системного пакета; запуск учебной программы не требует прав администратора. В последней команде `-c` означает «выполнить короткую строку кода Python». Если появляется `AESGCM ready`, импорт работает.

Если используешь отдельное виртуальное окружение Python, оно может не видеть системный пакет. Тогда устанавливай библиотеку внутри этого окружения его собственным `python -m pip install cryptography`. Не исправляй такую ситуацию случайной установкой в несколько разных Python. Сначала выясни, какой интерпретатор запускает файл.

## Сделай сейчас: Выполни опыт с тремя подменами

В Mousepad создай `aead_demo.py` в учебной папке:

```python
import os
from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)
message = b"amount=100"
aad = b"order=101"
cipher = AESGCM(key)
sealed = cipher.encrypt(nonce, message, aad)

print("valid:", cipher.decrypt(nonce, sealed, aad).decode("utf-8"))

changed = bytearray(sealed)
changed[0] ^= 1
cases = [
    ("ciphertext", nonce, bytes(changed), aad),
    ("aad", nonce, sealed, b"order=202"),
    ("nonce", bytes([nonce[0] ^ 1]) + nonce[1:], sealed, aad),
]
for label, test_nonce, test_data, test_aad in cases:
    try:
        cipher.decrypt(test_nonce, test_data, test_aad)
    except InvalidTag:
        print(label + ": rejected")
    else:
        raise RuntimeError("Unexpected acceptance: " + label)
```

`generate_key(bit_length=256)` создаёт ключ подходящей длины. `os.urandom(12)` выдаёт 12 случайных байт для nonce этого небольшого опыта. Для работающей системы правила выделения nonce, предельного количества сообщений и смены ключей проектируют отдельно; одной фразы «берём случайное» недостаточно для любой нагрузки.

`bytearray` создаёт изменяемую копию байтов. Операция `^= 1` переключает один бит первого байта. Мы намеренно портим уже зашифрованный результат и не выполняем второе шифрование с прежним nonce. Это разные действия: проверка повреждения шифротекста не требует нарушать правило уникальности nonce при шифровании.

Список `cases` содержит три опыта. В первом меняется шифротекст, во втором — открытый заголовок, в третьем — nonce, переданный при расшифровании. Цикл ловит именно `InvalidTag`. Ветка `else` у `try` выполняется, когда исключения не было: здесь это повод остановить опыт как неожиданно успешную подмену.

Запусти `python3 aead_demo.py`. Ожидаемый вывод:

```text
valid: amount=100
ciphertext: rejected
aad: rejected
nonce: rejected
```

Ключ и nonce на каждом новом запуске меняются, но эти четыре строки должны оставаться такими же. Мы не печатаем ключ, потому что для проверки поведения это не нужно.

## Сделай сейчас: Как правильно обработать отказ

`InvalidTag` не сообщает, какая именно причина была у ошибки: другой ключ, nonce, AAD или подмена содержимого. Приложение должно считать сообщение непроверенным и не использовать его. Нельзя показывать «частично получившийся текст», выполнять команду из него или сохранять его как достоверный заказ.

Если первый, обычный случай неожиданно падает, сверь входы: при расшифровании должны использоваться те же байты AAD, полный `sealed` и прежний nonce. Сохранение в файл требует формата, который однозначно хранит nonce и шифротекст с меткой; секретный ключ нельзя просто положить рядом в общедоступную папку и считать задачу решённой.

Здесь ключ живёт в памяти одного процесса. После завершения программы он исчезает, и отдельно сохранённый шифротекст без ключа расшифровать не получится. Это учебное свойство примера, а не готовая система резервного копирования ключей. Прежде чем шифровать реальные документы, нужно решить хранение, доступ, восстановление и смену ключей.

## Почему это работает: Как эти части связаны с TLS

HTTPS использует TLS для защиты канала между клиентом и сервером. У канала есть несколько разных задач: удостоверить сервер по имени и доверенной цепочке сертификатов, согласовать ключевой материал и защищать передаваемые записи. AEAD применяется к записям, но само по себе не отвечает на вопрос, с чьим сервером ты договорился о ключе.

Подумай о звонке в банк: шифрование разговора с посторонним, который представился банком, не превращает его в банк. Проверка сертификата и имени сервера важна вместе с шифрованием. В то же время корректный сертификат не доказывает, что приложение правильно проверяет права на заказы или не содержит SQL-инъекции. Канал и логика приложения требуют разных проверок.

Глава TLS в первом издании книги относится к состоянию протоколов на момент написания. Для современных деталей TLS 1.3 ориентируйся также на [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html), а для используемого интерфейса — на [документацию AESGCM](https://cryptography.io/en/latest/hazmat/primitives/aead/#cryptography.hazmat.primitives.ciphers.aead.AESGCM). Твоя задача после опыта — объяснить назначение каждого входа и причину отказа принимать непроверенный результат, а не написать собственный криптографический протокол.
