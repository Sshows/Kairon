## Перед началом: Три вопроса, которые часто смешивают

Тебе прислали файл заказа. Нужно понять, не изменился ли он, кто мог подтвердить его содержимое и могут ли посторонние его прочитать. Это три разных вопроса. Хеш помогает сравнивать содержимое. MAC, например HMAC, помогает проверить целостность и подлинность сообщения при наличии общего секрета. Шифрование решает вопрос скрытия содержимого. Одна функция не обязана делать всё сразу.

Представь посылку с запиской о её весе. Если посылка стала тяжелее, сравнение с доверенной записью обнаружит изменение. Но если посторонний заменит и содержимое, и записку с весом, сравнение с новой запиской ничего не докажет. Для защиты от такой подмены нужен доверенный источник контрольного значения или механизм, для которого требуется секрет.

Аналогия с весом имеет предел: одинаковый вес не гарантирует одинаковое содержимое. Криптографический хеш устроен гораздо сложнее весов, но и у него существуют совпадения: число возможных файлов больше числа выходных значений. Требуется, чтобы опасные совпадения было практически трудно находить, а не чтобы они математически не существовали. Именно поэтому в Serious Cryptography отдельно рассматриваются свойства хеш-функции и её применение в протоколе.

## Сделай сейчас: Начни с байтов, а не с внешнего вида текста

Открой терминал Kali и создай отдельную папку:

```bash
mkdir -p ~/kairon-reading/crypto
cd ~/kairon-reading/crypto
printf 'recipient=anna;amount=100\n' > order.txt
sha256sum order.txt
```

`printf` записывает учебный текст; `\n` добавляет перенос строки. `>` создаёт файл или заменяет прежнее содержимое. `sha256sum` вычисляет SHA-256 байтов файла. Результат состоит из 64 шестнадцатеричных символов и имени файла: 64 символа по 4 бита дают 256 бит. Имя файла в вычисляемое содержимое не входит.

Скопируй файл и сравни:

```bash
cp order.txt order-copy.txt
sha256sum order.txt order-copy.txt
printf 'recipient=anna;amount=900\n' > order-copy.txt
sha256sum order.txt order-copy.txt
```

Вначале хеши совпадают, после замены `100` на `900` — различаются. `cp` создаёт копию, а не ссылку на те же байты. Если просто переименовать неизменённый файл, хеш останется прежним. Перенос строки тоже является байтом: редактор, добавивший его в конце, действительно изменил файл, даже если на экране почти ничего не поменялось.

Хеш не является зашифрованной копией заказа. Из него нельзя штатно «расшифровать обратно» текст. При этом короткое предсказуемое содержимое иногда можно угадать перебором и сравнить хеши. Невозможность обратного расшифрования не означает невозможность проверки догадок.

## Почему это работает: Почему злоумышленник может заменить обычный хеш

Алгоритм SHA-256 открыт. Любой, у кого есть новый файл, может посчитать для него новый хеш. Поэтому файл и контрольная сумма, полученные из одного недоверенного места, не устанавливают автора. Для проверки загрузки важно, откуда получена исходная контрольная сумма: например, из доверенно доставленного подписанного списка.

HMAC добавляет общий секретный ключ. Отправитель вычисляет метку сообщения с ключом. Получатель, знающий тот же ключ, пересчитывает метку и сравнивает. Посторонний может прочитать открытый заказ и знать алгоритм, но без ключа не должен практически уметь создать правильную метку изменённого сообщения.

При этом **оба владельца общего ключа** умеют создавать метки. HMAC не позволяет независимому судье доказать, кто именно из них написал сообщение. Для иных свойств используются другие механизмы, например цифровые подписи. Называть любую метку «подписью» без уточнения — значит потерять это различие.

## Сделай сейчас: Проверь HMAC маленькой программой

Создай в Mousepad файл `mac_demo.py` в текущей папке:

```python
import hashlib
import hmac
from pathlib import Path

key = b"kairon-training-key-not-for-real-data"
original = Path("order.txt").read_bytes()
changed = Path("order-copy.txt").read_bytes()

tag = hmac.new(key, original, hashlib.sha256).hexdigest()
same_tag = hmac.new(key, original, hashlib.sha256).hexdigest()
changed_tag = hmac.new(key, changed, hashlib.sha256).hexdigest()

print("original:", hmac.compare_digest(tag, same_tag))
print("changed: ", hmac.compare_digest(tag, changed_tag))
print("readable message:", original.decode("utf-8").strip())
```

`b"..."` создаёт последовательность байтов. Ключ здесь публичный и учебный: он нужен для повторяемого опыта, а не для реального хранения секретов. В рабочей системе ключ генерируют подходящим криптографическим генератором, ограничивают доступ к нему и не публикуют в коде.

`read_bytes` читает содержимое без преобразования переносов строк и кодировок. `hmac.new` получает ключ, сообщение и выбранную хеш-функцию. `hexdigest` превращает метку в удобную для вывода шестнадцатеричную запись. Мы используем готовую реализацию HMAC, а не пытаемся заменить её выражением `sha256(key + message)`: внешне похожая формула не даёт автоматически тех же свойств безопасности.

`compare_digest` предназначена для сравнения таких значений и помогает избегать простого сравнения с зависимостью времени от совпавшего префикса. Она не делает весь сервис автоматически защищённым от любых атак по времени: остаются другие участки кода, ошибки и окружение.

Запусти `python3 mac_demo.py`. Ожидаются `original: True` и `changed: False`. Последняя строка покажет читаемый заказ: опыт специально демонстрирует, что HMAC **не шифрует** сообщение. Если `changed` тоже равен `True`, проверь, действительно ли ты изменил копию и не переписал оба файла одинаково.

## Почему это работает: Почему верная метка ещё не защищает от повтора

Допустим, правильное сообщение означает «перевести 100 единиц». Если получатель принимает одно и то же сообщение снова и снова, постороннему не нужно менять его содержимое или подделывать метку. Можно повторно предъявить уже корректную пару. Это повтор сообщения, или replay.

Чтобы отличить новое действие от повтора, протокол может включать в аутентифицируемые данные номер операции и хранить состояние уже обработанных номеров. Сам номер без проверки на стороне получателя не помогает. Временная метка тоже требует правил допустимого окна и учёта повторов; часы могут расходиться.

Не путай эту задачу с хранением паролей. Быстрый SHA-256 удобен для файлов, но позволяет быстро проверять догадки о слабом пароле. Для паролей нужны специальные функции выработки значения с солью и настраиваемой стоимостью, например Argon2id или scrypt при подходящем применении. Одинаково назвать всё «хешированием» недостаточно, чтобы выбрать правильный механизм.

## Сделай сейчас: Сформулируй границы результата

В отчёте запиши отдельно: «Байты копии изменились», «HMAC изменённого содержимого отличается от исходной», «Текст остаётся открытым», «Учебная программа не хранит историю операций и не защищает от replay». Это четыре конкретных наблюдения вместо одной слишком широкой фразы «данные защищены».

Частые причины несовпадения меток у честных участников — другой ключ, кодировка, перенос строки, порядок полей при повторном формировании JSON. Стороны должны договориться, **какие именно байты** аутентифицируются. Если одна сторона подписывает один JSON-текст, а другая заново собирает его с другими пробелами, логически одинаковые данные могут дать разные метки. Следующее занятие добавит скрытие содержимого и покажет, как шифрование сочетается с проверкой подлинности.
