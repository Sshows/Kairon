## Перед началом: Почему не стоит начинать с самого сложного инструмента

Тебе дали установочный пакет программы и попросили разобраться, где обрабатываются пользовательские данные. Первая мысль — открыть самый известный декомпилятор. Но сначала полезно узнать, что именно находится внутри: текстовые скрипты, байткод виртуальной машины, машинный код или смесь этих вариантов.

Представь коробку с документацией от прибора. В ней может лежать инструкция на русском, схема условными обозначениями или готовая электронная плата. Для инструкции нужен читатель, для схемы — знание обозначений, для платы — другие инструменты. Если сразу смотреть на плату, можно пропустить лежащую рядом подробную инструкцию.

Предоставленная глава 4 From Day Zero to Zero Day строится вокруг такого выбора направления. Electron-приложение может содержать JavaScript в ASAR, программа PyInstaller — упакованный Python и интерпретатор, Java-приложение — байткод, а обычный ELF — машинные инструкции и метаданные. В одном продукте иногда есть несколько типов сразу. Задача первичного разбора — составить карту, чтобы выбирать следующий шаг обоснованно.

## Почему это работает: Различай три представления

**Исходный код** записан на языке, понятном разработчику: имена переменных, функции, условия, комментарии. Скрипт исполняется соответствующей средой. Это не означает, что внутри среды нет компиляции: например, Python и JavaScript могут создавать промежуточные представления или машинный код во время работы.

**Байткод** — инструкции для определённой виртуальной машины или интерпретатора. Процессор обычно не исполняет их напрямую как инструкции своей архитектуры. Среда выполнения понимает формат и выполняет необходимые действия. Инструменты для Java-байткода, .NET и CPython различаются: слово «байткод» не задаёт один универсальный формат.

**Машинный код** — инструкции для конкретной архитектуры процессора. Ассемблер — читаемая человеком запись этих инструкций. Дизассемблер показывает такое представление. Декомпилятор пытается восстановить более высокоуровневый псевдокод. Комментарии, исходные имена и точная структура программы могут быть потеряны, а компилятор мог преобразовать логику ради оптимизации.

Разница важна практически. Если рядом с исполняемым Electron-файлом есть `resources/app.asar`, следующий полезный вопрос — что содержит архив и где точка входа JavaScript. Если это Java JAR, сначала рассматривают его структуру и метаданные. Если это ELF, пригодятся сведения о секциях, символах и импортируемых функциях. Расширение файла — подсказка, которую нужно сверить с содержимым.

## Сделай сейчас: Сделай карту маленького собственного приложения

Открой терминал Kali:

```bash
mkdir -p ~/kairon-reading/binary-map
cd ~/kairon-reading/binary-map
```

В Mousepad создай файл `manifest.json`:

```json
{
  "name": "training-orders",
  "entry": "orders.py",
  "data": "orders.json"
}
```

Это собственный учебный формат описания приложения, а не обязательный стандарт Python. Поле `entry` подсказывает, с какого файла начинает работать наш пример; `data` указывает данные. Метаданные экономят время: вместо случайного чтения всех файлов можно найти точку входа и затем проследить вызовы.

Рядом создай `orders.py`:

```python
def can_read(actor, owner):
    return actor == owner
```

Здесь нет сети и настоящих заказов. Функция принимает действующего пользователя и владельца объекта, сравнивает их и возвращает логическое значение. `==` сравнивает значения; одиночный `=` в Python используется при присваивании. Пока мы только записали функцию в файл: её создание не равно выполнению проверки с конкретными аргументами.

В терминале выполни `file orders.py` и `cat manifest.json`. Первая команда определяет предполагаемый тип файла по содержимому, вторая показывает данные манифеста. Теперь в карте уже есть связь: «описание → точка входа → функция принятия решения». Этого достаточно, чтобы начать предметное чтение.

## Сделай сейчас: Посмотри структуру исходника и байткод

Создай третий файл `inspect_code.py`:

```python
import ast
import dis
import types
from pathlib import Path

source = Path("orders.py").read_text(encoding="utf-8")
tree = ast.parse(source, filename="orders.py")
print("FUNCTIONS:", [node.name for node in tree.body if isinstance(node, ast.FunctionDef)])

module_code = compile(tree, "orders.py", "exec")
function_code = next(item for item in module_code.co_consts if isinstance(item, types.CodeType))
dis.dis(function_code)
```

`ast.parse` разбирает синтаксис в дерево. Узел `FunctionDef` означает определение функции; список должен содержать `can_read`. `compile` создаёт объект кода CPython. Строка `"exec"` здесь выбирает режим компиляции модуля: это **не вызов функции `exec`** и не выполнение исследуемого файла. `co_consts` содержит константы и вложенные объекты кода, из которых мы выбираем код нашей единственной функции.

`dis.dis` выводит байткод для этого объекта. Запусти `python3 inspect_code.py`. В разных версиях CPython названия служебных инструкций и смещения отличаются. Ищи смысловую последовательность: загрузить два аргумента, сравнить их и вернуть результат. Не требуется, чтобы номера строк и байтов в точности совпали с чужим скриншотом.

Это позволяет увидеть несколько уровней одной небольшой логики. Исходник показывает имена `actor` и `owner`; синтаксическое дерево — конструкцию функции; байткод — операции среды выполнения. Для данного опыта мы сами создали исходник, поэтому можем надёжно сверить представления. При анализе чужого скомпилированного файла исходника может не быть.

## Почему это работает: Почему реконструкция не является оригиналом

В главе приводится пример, когда привычный вызов `printf` после оптимизации представлен как `puts`. Это не обязательно ошибка декомпилятора: сам компилятор мог выбрать эквивалентную реализацию. Статическая линковка добавляет код библиотек внутрь результата, динамическая оставляет связи с внешними библиотеками. Удаление символов уменьшает доступные имена, а упаковка может скрыть исходное представление за распаковщиком.

Отсюда несколько практических выводов. Огромная функция или странные имена в псевдокоде не доказывают злой умысел автора. Наличие библиотеки не доказывает достижимость каждой её функции. Упоминание интересного порта в исходниках ещё не означает, что приложение действительно открывает его при запуске: в предоставленной главе отдельно разбирается случай неиспользуемого компонента.

Если `inspect_code.py` сообщает `SyntaxError`, проверь исходный файл и отступы. Если `StopIteration`, вероятно, ты убрал единственную функцию или изменил пример так, что в константах больше нет ожидаемого объекта кода. Если байткод другой версии, сначала запиши `python3 --version` и сравнивай поведение, а не номера инструкций.

Результат занятия — карта файлов и объяснение одного пути данных через несколько представлений. Дальше можно выбирать конкретный вопрос безопасности: например, откуда приходит имя выходного файла и что ограничивает папку записи. Именно такой путь мы проследим в следующем занятии, чтобы перейти от «интересного кода» к проверяемой ошибке.
