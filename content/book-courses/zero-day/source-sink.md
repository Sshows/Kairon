## Перед началом: Найти подозрительную строку — только начало

Допустим, приложение принимает имя файла от пользователя и сохраняет результат обработки в папку отчётов. Нужное правило звучит просто: пользователь выбирает имя **внутри разрешённой папки**, а не место записи в любой части системы. Для проверки нужно проследить путь значения от источника до операции записи.

В анализе часто используют слова **source** и **sink**. Source — место, где появляется недоверенное значение: параметр запроса, поле файла, сообщение. Sink — действие, для которого это значение важно: запись файла, SQL-запрос, выдача приватных данных. Между ними могут быть преобразования и проверки. Само наличие source и sink не доказывает ошибку; нужно установить, что запрещённое значение действительно может дойти до действия.

Представь службу доставки, где клиент пишет номер ячейки для своей посылки. Сотрудник должен выбрать ячейку в разрешённом отделении. Если он воспринимает поле как произвольную инструкцию «выйти в соседнее здание», граница нарушена. Проверять нужно итоговое место назначения, а не только наличие красивого слова в начале записки.

В предоставленной главе обсуждаются метаданные, восстановление исходников и работа с путями при разборе source map. Здесь мы применим тот же принцип внимательного чтения границ к собственному небольшому примеру. Это самостоятельная практика Kairon, а не заявление о новой уязвимости автора книги или реального продукта.

## Почему это работает: Пойми нормализацию пути

Путь `reports/note.txt` указывает на файл внутри `reports`. Компонент `..` обычно означает переход к родительской папке. Поэтому путь `reports/../other/note.txt` после нормализации выходит в `other`. Абсолютный путь задаёт начало от корня файловой системы и может вообще не использовать предполагаемую базовую папку.

Проверка строкового префикса выглядит заманчиво: если итог начинается с `/tmp/reports`, значит, он внутри? Но соседняя папка `/tmp/reports-old` тоже начинается с этих символов. Строковое отношение «начинается с» не совпадает с файловым отношением «является потомком папки».

Символические ссылки добавляют ещё один слой: видимый путь внутри папки может вести наружу. Поэтому важно понимать, проверяется ли строка или фактическое нормализованное назначение и может ли кто-то менять ссылки между проверкой и записью. В опыте ниже временной папкой управляет только наша программа. Для сервиса с недоверенными конкурентными изменениями понадобятся дополнительные средства безопасного открытия файлов.

## Сделай сейчас: Построй опыт в временной папке

Открой терминал Kali и создай учебную папку:

```bash
mkdir -p ~/kairon-reading/paths
cd ~/kairon-reading/paths
```

В Mousepad создай `path_review.py`:

```python
from pathlib import Path
from tempfile import TemporaryDirectory

def safe_target(root, user_name):
    relative = Path(user_name)
    if relative.is_absolute():
        raise ValueError("Absolute path is not allowed")
    root = root.resolve()
    candidate = (root / relative).resolve()
    if candidate == root or not candidate.is_relative_to(root):
        raise ValueError("Outside the report directory")
    return candidate

with TemporaryDirectory(prefix="kairon-path-review-") as location:
    base = Path(location)
    reports = (base / "reports").resolve()
    reports.mkdir()
    (base / "reports-old").mkdir()

    wrong = (reports / "../reports-old/stolen.txt").resolve()
    print("string-prefix-check:", str(wrong).startswith(str(reports.resolve())))
    for name in ["note.txt", "sub/note.txt", "../reports-old/stolen.txt", "../outside.txt", str(base / "absolute.txt")]:
        try:
            destination = safe_target(reports, name)
        except ValueError:
            print(name, "REJECT")
        else:
            print(name, "ALLOW", destination.relative_to(reports))
```

`TemporaryDirectory` создаёт отдельную временную папку и удалит её при выходе из блока `with`. Программа не записывает файл с названием `stolen.txt` — это только строка для проверки. Мы создаём лишь две собственные пустые папки во временном каталоге. Обычный запуск не требует `sudo`.

`Path(user_name)` представляет путь. Сначала политика запрещает абсолютный вариант. `root / relative` соединяет базу и относительное имя. `resolve` нормализует путь и разрешает существующие символические ссылки. `is_relative_to` проверяет файловое отношение после этой нормализации. Отдельно отклоняется сама корневая папка, потому что ожидается путь к файлу, а не команда выбрать каталог целиком.

`raise ValueError` прекращает текущий выбор назначения. Обработчик `except` в проверяющем цикле превращает отказ в понятную строку. В нормальном сервисе после отказа не должно происходить записи по первоначальному непроверенному имени. Иначе проверка будет существовать только «для галочки» и никак не ограничит действие.

## Сделай сейчас: Прочитай ожидаемый вывод

Запусти `python3 path_review.py`. Первая строка должна показать `string-prefix-check: True`. Это демонстрация слабости проверки строкового начала: соседняя папка ошибочно прошла бы такой фильтр.

Далее `note.txt` и `sub/note.txt` получат `ALLOW`. Переходы к соседней папке и за пределы `reports` получат `REJECT`. Абсолютный путь тоже отклоняется; начало временного пути у тебя будет собственным. Само слово `ALLOW` в этом опыте означает разрешённое назначение, а не выполненную запись. Программа намеренно сначала проверяет правило отдельно от файлового действия.

Теперь добавь вариант `sub/../note.txt`. После нормализации он остаётся внутри `reports` и при нашей политике может быть разрешён. Это показывает, почему правило «любое наличие двух точек равно атака» слишком грубое. Некоторые продукты намеренно запрещают любые вложенные компоненты и разрешают лишь простое имя; это тоже допустимая политика, если она ясна и проверена в общем месте обработки.

## Сделай сейчас: Проследи значение до реального действия

Нарисуй в заметке цепочку: `user_name → Path → соединение с reports → resolve → проверка принадлежности → возвращённый destination`. Если позже добавишь запись, она должна использовать именно проверенный `destination`. Повторное использование исходного `user_name` после проверки может вернуть прежнюю ошибку.

Для настоящего веб-сервиса добавляются вопросы: кто управляет каталогом, доступны ли ссылки, могут ли другие процессы изменить файловую систему, требуется ли создавать вложенные папки, можно ли перезаписывать существующий отчёт. Без этих условий нельзя объявить показанную функцию универсально безопасной для любого приложения. В системах с конкурентным недоверенным доступом проверка и открытие пути должны учитывать гонки и механизмы операционной системы.

Аналогичный ход рассуждения работает в других задачах. Для IDOR прослеживают номер объекта до выдачи данных и ищут проверку владельца. Для SQL — параметр до выполнения запроса и способ его передачи. Для вывода HTML — текст до интерпретации браузером и контекст экранирования. Нельзя заменить разбор этих границ поиском одного «плохого слова» по исходникам.

## Сделай сейчас: Оформи вывод и проверь обычную работу

Твой отчёт должен назвать источник значения, чувствительное действие, требуемую границу и минимальные случаи. В нашем опыте: «Строковый префикс разрешает соседнюю папку с похожим началом имени. Нормализованный путь проверяется как потомок `reports`; обычный и вложенный разрешённые пути остаются доступны».

`AttributeError` для `is_relative_to` может означать слишком старую версию Python: метод доступен начиная с Python 3.9. Ошибка синтаксиса или отступов требует сначала сверить файл, а не менять права каталогов. Если работаешь на другой ОС, разделители путей и правила абсолютных имён отличаются; используй средства `pathlib` соответствующей системы и формулируй тесты под её файловую модель.

Результат занятия — объяснение найденного дефекта, проверка альтернативного входа и нормального сценария. Это небольшая, но законченная работа исследователя: от чтения механизма до проверяемой гипотезы, исправления и ограничения того, что действительно доказано.
