## Перед началом: Почему правильного запроса бывает недостаточно

Приложение может правильно обрабатывать каждое действие по отдельности и ошибаться в их порядке. Купон ещё не использован? Проверка говорит «да». Применить скидку? Тоже допустимое действие. Но если две покупки одновременно прошли проверку до отметки об использовании, одноразовый купон сработает дважды.

Представь два кассовых окна и последнюю свободную ячейку хранения. Каждый кассир посмотрел на доску до того, как другой успел её исправить. Оба выдали один номерок разным людям. Повторное чтение одной и той же старой записи — причина конфликта. В программе такую зависимость от порядка называют **гонкой**, или race condition.

**TOCTOU** означает «время проверки — время использования». Между проверкой условия и действием условие могло измениться. Любая гонка не обязана быть именно TOCTOU, но купон хорошо показывает этот вариант. Она бывает и в файлах, и в базах, и в сложных распределённых процессах. Нам сначала нужно научиться описывать конкретную нарушенную гарантию.

## Сделай сейчас: Практика: сделай конфликт воспроизводимым

Вместо соревнования мышкой смоделируем точный порядок двух обработчиков. Затем сравним его с условным изменением одной записи в SQLite. Это локальный учебный код, запросов к магазину и настоящих покупок нет.

```python
import sqlite3

unused = True
request_a_saw_unused = unused
request_b_saw_unused = unused
issued = 0
for observed in [request_a_saw_unused, request_b_saw_unused]:
    if observed:
        issued += 1
        unused = False
print("split_check_issued=", issued)

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE coupon (id TEXT PRIMARY KEY, used INTEGER NOT NULL)")
db.execute("INSERT INTO coupon VALUES ('demo', 0)")
accepted = []
for request in ["a", "b"]:
    changed = db.execute(
        "UPDATE coupon SET used=1 WHERE id=? AND used=0", ("demo",)
    ).rowcount
    accepted.append(changed == 1)
print("atomic_results=", accepted)
print("atomic_issued=", sum(accepted))
db.close()
```

Запусти `python3 lab.py`. Первая строка должна показать `split_check_issued= 2`. Оба обработчика использовали ранее прочитанное True, даже после изменения `unused`. Это **явно заданное чередование**, а не нагрузочный тест и не настоящие параллельные HTTP-запросы. Его достоинство — каждый раз видна одна и та же причина.

Во второй части ожидается `atomic_results= [True, False]` и `atomic_issued= 1`. `:memory:` создаёт базу только в памяти процесса. Условие `used=0` и изменение `used=1` входят в **один UPDATE**. `rowcount` сообщает, сколько строк изменилось. Первый запрос изменил одну, второй уже не нашёл подходящую. В реальном сервисе выдача результата должна быть согласована с транзакцией: нельзя сначала отдать товар, а потом узнать, что обновление откатилось.

Повтори цикл второго опыта три раза вместо двух: успешной по-прежнему должна быть одна попытка. Затем убери `AND used=0` только для отдельного сравнения: все обращения смогут обновить запись, и ограничение исчезнет. Восстанови условие. Если видишь `no such table`, проверь, не создаёшь ли новое соединение `:memory:` перед UPDATE: у новой базы нет прежней таблицы.

## Почему это работает: Бизнес-логика: проверяй правило, а не только форму запроса

**Бизнес-правило** описывает допустимый процесс: купон применяется один раз, возврат не превышает оплату, заказ после отправки нельзя бесконтрольно менять. Нарушение такого правила не обязано содержать SQL-инъекцию или технически неверный HTTP. Запрос может быть синтаксически безупречным.

Запиши инвариант — утверждение, которое должно оставаться верным после любой разрешённой последовательности. Для купона: число успешных списаний не больше одного. Для остатка: количество не становится отрицательным. Затем составь пару нормальных и пару граничных последовательностей на своём стенде. Важно проверять итоговое состояние, а не только два ответа 200: один из них может обозначать повтор уже выполненной операции.

Идемпотентность означает, что повтор того же действия с тем же идентификатором не создаёт новый эффект. Ключ идемпотентности помогает пережить повтор после сетевого сбоя, но его нужно связывать с пользователем и конкретным действием и сохранять атомарно. Просто добавить поле в JSON недостаточно.

## Почему это работает: OAuth: что именно возвращается после согласия

OAuth даёт приложению ограниченное разрешение действовать через другой сервис. Это не передача пароля тому приложению. В схеме Authorization Code браузер получает короткоживущий код, приложение обменивает его на токены у сервера авторизации. **PKCE** связывает обмен кода с инициатором, знающим исходный verifier. Проверка точного `redirect_uri` ограничивает адрес возврата. Связывание ответа с начатой попыткой защищает от подмены контекста; в типичной схеме участвует `state`, а для идентичности в OpenID Connect есть свои проверки, включая issuer, audience и nonce.

Не путай OAuth и OpenID Connect: первый прежде всего про делегирование доступа, второй добавляет протокол удостоверения личности. Нельзя брать произвольный токен из URL и считать его доказательством входа. Конкретный набор проверок задаёт используемый протокол и библиотека. Книга 2019 года помогает понять исторические ошибки; актуальные требования сверяем с RFC 9700, а не переносим старые варианты потока без изменений.

Для учебного разбора нарисуй четыре участника: браузер, приложение, сервер авторизации, API. Подпиши, кто видит код и кто обменивает его. Затем назови, что пойдёт не так при разрешении любого адреса возврата, и где хранится связь с начатой попыткой входа. Настоящие токены и аккаунты для этой схемы не нужны.

## Перед началом: Забытый поддомен: запись ещё есть, услуги уже нет

**Subdomain takeover** может возникнуть, если DNS продолжает указывать на сторонний ресурс, который удалили, а провайдер позволяет другому владельцу занять подходящую привязку. Пустая страница или NXDOMAIN сами по себе этого не доказывают: возможность повторной привязки зависит от сервиса и проверки владения доменом.

Защитный разбор начинается с инвентаризации собственных DNS-записей и жизненного цикла ресурсов. При отключении услуги убирают устаревшую ссылку; включают доступные проверки владения. Не нужно регистрировать чужой ресурс ради любопытства. В отчёте о своём стенде достаточно зафиксировать запись, целевую услугу, подтверждённое состояние и порядок исправления.
