## Перед началом: Почему в компьютере сложение двух положительных чисел может дать отрицательное число

В модулях **Nibbling on Numbers** и **Numbers as Strings** курса **Computing 101** (`pwn.college`) разбирают то, как процессор на самом деле хранит числа в регистрах и памяти: чем байт числа `0x35` отличается от ASCII-символа цифры `'5'`, как устроен **дополнительный код (Two's Complement)** для отрицательных чисел и почему **целочисленное переполнение (Integer Overflow / Underflow)** — одна из самых опасных ошибок при проверке длины буфера.

Представь механический автомобильный счётчик пробега (одометр), рассчитанный ровно на три цифры — от `000` до `999`. Когда на счётчике горит `999` и машина проезжает ещё 2 километра, четвёртому колесику просто негде появиться: старший разряд сбрасывается, и счётчик показывает `001`!

В процессоре каждый регистр и каждая переменная C/C++/Rust тоже имеют фиксированную ширину — например, 8 бит (1 байт, `0..255`), 32 бита (`uint32_t`) или 64 бита (`uint64_t`). Если программа проверяет условие `if (header_len + body_len <= 64)` в 8-битной или 32-битной арифметике, а пользователь передаёт `header_len = 16` и `body_len = 250`, то сумма `16 + 250 = 266` в 8-битном счётчике сбрасывается по модулю $256$ и превращается в крошечное число `10`! Проверка `10 <= 64` радостно проходит, а в функцию копирования уходит длина `250`, вызывая переполнение буфера!

## Почему это работает: Беззнаковые числа, дополнительный код (Two's Complement) и ASCII-цифры

Разберём три фундаментальных правила представления чисел в памяти:

1. **Беззнаковые (`unsigned`) и знаковые (`signed`) числа в одних и тех же битах**. Возьмём один байт (8 бит):
   - если программа рассматривает его как **беззнаковое число (`uint8_t`)**, все 8 бит кодируют значения от `0` (`0x00`) до `255` (`0xFF`);
   - если программа рассматривает тот же байт как **знаковое число (`int8_t`, дополнительный код / Two's Complement)**, то старший 7-й бит (`0x80`) служит **знаковым битом (Sign Bit)**: значения от `0x00` до `0x7F` — это положительные числа от `0` до `+127`, а значения от `0x80` до `0xFF` — это отрицательные числа от `-128` до `-1` (по формуле $\text{signed} = \text{unsigned} - 256$). В частности, байт `0xFF` (`11111111` в двоичном виде) одновременно равен `255` без знака и `-1` со знаком!
2. **Почему процессоры используют именно дополнительный код (Two's Complement)**. Главное достоинство дополнительного кода в том, что одна и та же аппаратная схема сумматора складывает положительные и отрицательные числа без всяких отдельных правил: например, `5 + (-1)` в 8 битах — это `0x05 + 0xFF = 0x104`, а после отбрасывания переполненного 9-го бита остаётся ровно `0x04` (`4`)! Чтобы поменять знак числа в дополнительном коде, достаточно инвертировать все его биты и прибавить единицу: `-x = (~x + 1) & 0xFF`.
3. **Чем число в памяти отличается от числа в виде текста (`Numbers as Strings`)**. Число `42` в одном байте памяти — это байт `0x2A`. А строка `"42"`, которую человек вводит с клавиатуры, состоит из **двух байтов ASCII**: символа `'4'` (код `0x34`, то есть `0x30 + 4`) и символа `'2'` (код `0x32`, то есть `0x30 + 2`). Любая ASCII-цифра от `'0'` до `'9'` имеет код от `0x30` (`48`) до `0x39` (`57`), поэтому перевод одного символа цифры в число на ассемблере и C — это просто вычитание `0x30` (`byte - ord('0')`).

## Сделай сейчас: Практика: проверь дополнительный код, целочисленное переполнение и защиту проверки суммы

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
def to_int8_twos_complement(byte_val):
    u = byte_val & 0xFF
    return u - 256 if u >= 0x80 else u


def vulnerable_u8_size_check(header_len, body_len, max_buf=64):
    wrapped_total = (header_len + body_len) & 0xFF
    if wrapped_total <= max_buf:
        return f"passed_buggy_check:wrapped_total={wrapped_total}:actual_copy={body_len}"
    return "rejected:too_large"


def safe_size_check(header_len, body_len, max_buf=64):
    if not (0 <= header_len <= max_buf and 0 <= body_len <= max_buf - header_len):
        return "rejected:safe_overflow_free_check"
    return f"accepted:total={header_len + body_len}"


def ascii_digits_to_int(ascii_bytes):
    value = 0
    for b in ascii_bytes:
        value = value * 10 + (b - 0x30)
    return value


print("byte_0xff_views= unsigned:", 0xFF, "signed_int8:", to_int8_twos_complement(0xFF))
print("byte_0x80_views= unsigned:", 0x80, "signed_int8:", to_int8_twos_complement(0x80))
print("overflow_bug=", vulnerable_u8_size_check(16, 250, max_buf=64))
print("safe_check=", safe_size_check(16, 250, max_buf=64))
print("ascii_parsed=", ascii_digits_to_int(b"1337"))
```

### Шаг 2. Запусти программу и изучи поведение разрядов

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
byte_0xff_views= unsigned: 255 signed_int8: -1
byte_0x80_views= unsigned: 128 signed_int8: -128
overflow_bug= passed_buggy_check:wrapped_total=10:actual_copy=250
safe_check= rejected:safe_overflow_free_check
ascii_parsed= 1337
```

Разберём вывод по шагам:
- один и тот же байт `0xFF` равен `255` при беззнаковом чтении и `-1` в 8-битном дополнительном коде (`to_int8_twos_complement`), а `0x80` (`128`) представляет минимальное отрицательное число `-128`;
- в `overflow_bug` сумма `16 + 250 = 266` при усечении до 8 бит (`& 0xFF`) превратилась в `10`, обманув наивную проверку `wrapped_total <= 64`;
- в `safe_size_check` проверка записана **без опасного сложения**: сначала проверяется `0 <= header_len <= max_buf`, а затем `body_len <= max_buf - header_len`. Так как `max_buf >= header_len`, вычитание `max_buf - header_len` никогда не переполняется, и `body_len = 250` надёжно отклоняется (`rejected:safe_overflow_free_check`);
- функция `ascii_digits_to_int` перевела четыре ASCII-байта `b"1337"` (`0x31 0x33 0x33 0x37`) в целое число `1337`, вычитая из каждого байта `0x30` и умножая аккумулятор на `10`.

### Шаг 3. Проверь допустимый размер пакета и перевод чисел в Kali

В файле `lab.py` измени `250` в вызове `safe_size_check(16, 250, max_buf=64)` на `32`, сохрани и запусти `python3 lab.py`. Теперь `32 <= 64 - 16`, и безопасная проверка вернёт `accepted:total=48`. После проверки верни `250`.

В терминале Kali ты можешь в любой момент посмотреть знаковое и беззнаковое представление 1-, 2-, 4- и 8-байтовых чисел через стандартный модуль `struct`:

```bash
python3 -c 'import struct; raw = b"\xff\xff\xff\xff"; print("uint32=", struct.unpack("<I", raw)[0], "int32=", struct.unpack("<i", raw)[0])'
```

Ты увидишь, что четыре байта `\xff\xff\xff\xff` — это одновременно `4294967295` (`uint32`) и `-1` (`int32`).

## Почему это работает: Как защищать арифметику размеров при выделении памяти

Классическая уязвимость выделения памяти возникает и при умножении `malloc(count * element_size)`: если `count * element_size` переполняет 32-битный или 64-битный регистр, `malloc` выделяет крошечный буфер, а цикл заполнения пишет `count` элементов за его границу. Поэтому вместо ручного умножения `malloc(n * size)` в C используют функцию **`calloc(n, size)`** (которая сама проверяет переполнение при умножении и обнуляет память) или встроенные безопасные функции проверки переполнения `__builtin_add_overflow` / `checked_add` в Rust.

## Если не получилось: Частые ошибки

- **Почему в Python обычное сложение `16 + 250` не переполняется само**: в Python тип `int` имеет произвольную точность (автоветвление разрядности), поэтому переполнение в модели мы явно покажем битовой маской разрядности регистра (`& 0xFF` для 8 бит, `& 0xFFFFFFFF` для 32 бит или `& ((1 << 64) - 1)` для 64 бит). А вот в языках C, C++, Go и в регистрах процессора `x86-64`/`ARM64` разрядность фиксирована аппаратно.
