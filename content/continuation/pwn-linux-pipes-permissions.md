## Перед началом: Как программы передают данные друг другу и проверяют права

В прошлом уроке мы разобрали, как оболочка находит команду и передаёт ей аргументы. Но после запуска у каждого процесса в Linux появляются три стандартных канала связи и набор полномочий (от чьего имени процесс имеет право открывать файлы).

Представь цех с конвейерной лентой. У каждого рабочего есть:
- **входной лоток (`stdin`, дескриптор `0`)** — откуда он берёт заготовки;
- **выходной лоток (`stdout`, дескриптор `1`)** — куда он кладёт готовые детали;
- **журнал замечаний (`stderr`, дескриптор `2`)** — куда он отдельно записывает поломки, чтобы сообщения об ошибках не смешивались с готовыми деталями на ленте.

В курсе **Linux Luminarium** на `pwn.college` (модули `Piping`, `Processes`, `Users`, `Permissions` и `Shenanigans`, лицензия BSD-2-Clause) на этом строятся десятки практических задач: перенаправить стандартный ввод из одного файла, ошибки — в другой, соединить две программы трубой (`|`) и понять, почему специальный бит `setuid` временно даёт процессу права владельца файла.

## Почему это работает: Дескрипторы 0/1/2, конвейеры и бит setuid (0o4000)

Разберём механизмы по шагам:

1. **Разделение `stdout` (1) и `stderr` (2)**. Когда ты пишешь `команда > out.txt`, в файл попадает только обычный вывод (`stdout`, канал 1). Ошибки (`stderr`, канал 2) продолжают печататься на экране, чтобы ты не пропустил сбой. Если нужно записать ошибки в отдельный файл, пишут `2> err.txt`. А запись `2>&1` направляет поток ошибок туда же, куда сейчас направлен обычный вывод.
2. **Конвейер (`|`, pipe)**. Знак `|` соединяет `stdout` левой команды со `stdin` правой команды напрямую через буфер в памяти ядра, без создания временного файла на диске. При этом важно помнить, что обычный `|` передаёт только `stdout` (канал 1), а `stderr` (канал 2) по умолчанию идёт мимо трубы.
3. **Права POSIX и бит `setuid`**. Обычные права файла записываются тремя тройками бит `rwx` (чтение `4`, запись `2`, выполнение `1`) для владельца (`user`), группы (`group`) и остальных (`other`), например `0o755` (`rwxr-xr-x`). Но перед ними есть ещё одна старшая восьмеричная цифра специальных битов: `4` (`0o4000`, `setuid`), `2` (`0o2000`, `setgid`) и `1` (`0o1000`, `sticky bit`). Когда у исполняемого файла включён бит `setuid` (в `ls -l` вместо `x` у владельца видна буква `s`, например `-rwsr-xr-x`), при запуске его **эффективный идентификатор пользователя (`euid`)** становится равен владельцу файла, а **реальный (`ruid`)** остаётся твоим. Так работает, например, системная утилита `passwd`: чтобы обычный пользователь мог изменить свой пароль в защищённом файле, программа запускается с привилегиями владельца и строго проверяет, чью именно запись разрешено менять.

## Сделай сейчас: Практика: промоделируй конвейер потоков и эффективные права запуска

### Шаг 1. Сохрани код модели в файл `lab.py`

Вставь следующий код в открытое окно редактора Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
import stat

raw_lines = [
    ("stdout", "OK: user=alice action=read"),
    ("stderr", "WARN: deprecated flag ignored"),
    ("stdout", "OK: user=bob action=write"),
    ("stdout", "SKIP: healthcheck"),
]

stdout_pipe = [text for stream, text in raw_lines if stream == "stdout"]
stderr_log = [text for stream, text in raw_lines if stream == "stderr"]
filtered_ok = [line for line in stdout_pipe if line.startswith("OK:")]
print("stdout_count=", len(stdout_pipe), "stderr_count=", len(stderr_log))
print("piped_ok=", len(filtered_ok))


def effective_uid(caller_uid, file_owner_uid, mode):
    is_executable = bool(mode & (stat.S_IXUSR | stat.S_IXGRP | stat.S_IXOTH))
    if not is_executable:
        return None
    if mode & stat.S_ISUID:
        return file_owner_uid
    return caller_uid


normal_mode = 0o0755
suid_mode = 0o4755
print("normal_perm=", stat.filemode(stat.S_IFREG | normal_mode), "euid=", effective_uid(1000, 0, normal_mode))
print("suid_perm=", stat.filemode(stat.S_IFREG | suid_mode), "euid=", effective_uid(1000, 0, suid_mode))
```

### Шаг 2. Запусти скрипт и проверь каждую строку

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
stdout_count= 3 stderr_count= 1
piped_ok= 2
normal_perm= -rwxr-xr-x euid= 1000
suid_perm= -rwsr-xr-x euid= 0
```

Разберём, что показала программа:
- из четырёх строк процесса три вышли в `stdout` и одна (`WARN: ...`) — в `stderr`. Поэтому следующая команда конвейера увидела только 3 строки `stdout` и отобрала из них 2 строки `OK:`;
- функция `stat.filemode` из стандартной библиотеки Python переводит числовую маску прав в знакомую строку `ls -l`: для `0o0755` это `-rwxr-xr-x`, а для `0o4755` — `-rwsr-xr-x` (обрати внимание на букву `s` в первой тройке `rws`);
- при обычном запуске пользователем `1000` эффективный `euid` остаётся `1000`, а при наличии бита `stat.S_ISUID` (`0o4000`) становится равен владельцу файла (`0`).

### Шаг 3. Проверь снятие бита `setuid` и настоящие потоки в терминале

В файле `lab.py` замени `suid_mode = 0o4755` на `suid_mode = 0o0755`, сохрани и запусти `python3 lab.py` ещё раз. Теперь обе строки покажут `-rwxr-xr-x` и `euid= 1000`. После проверки верни `0o4755` обратно и убедись, что снова выводится `-rwsr-xr-x euid= 0`.

Дополнительно в том же терминале Kali можешь проверить настоящее разделение `stdout` и `stderr` одной безопасной командой:

```bash
ls . ./no-such-file > out.txt 2> err.txt && head -n 5 out.txt err.txt
```

В `out.txt` окажется список файлов текущей папки (`lab.py`), а в `err.txt` — сообщение об отсутствующем файле `./no-such-file`.

## Почему это работает: Зачем аналитику проверять биты SUID и потоки ввода-вывода

В модуле `Permissions` курса **Linux Luminarium** и в задачах аудита Linux-систем бит `setuid` рассматривают с двух сторон:
- **со стороны архитектуры ОС**: это штатный механизм, позволяющий маленькой проверенной программе выполнить строго одно привилегированное действие (например, пропинговать узел или сменить пароль);
- **со стороны защиты**: если `setuid`-программа позволяет пользователю указать произвольный путь для записи, подгрузить свою библиотеку или вызвать оболочку `/bin/sh`, то эта дочерняя операция унаследует повышенный `euid`. Именно поэтому при настройке сервера лишние биты `setuid` убирают командой `chmod u-s файл`, а поиск всех таких файлов в системе проводят через `find / -perm -4000 2>/dev/null` (где `2>/dev/null` как раз убирает шум отказов доступа из канала ошибок `stderr`).

## Если не получилось: Частые ошибки

- **Пустой файл при перенаправлении ошибки через `>`**: обычный знак `>` перенаправляет только поток `1` (`stdout`). Для потока ошибок `stderr` обязательно пиши `2>` без пробела между двойкой и знаком больше.
- **Буква `S` заглавная вместо строчной `s` в правах `-rwSr-xr-x`**: заглавная `S` означает, что бит `setuid` (`0o4000`) поставили на файл, у которого выключен сам бит выполнения владельца (`0o0100`). Без права выполнения программа не запустится.
