## Шифр обрабатывает блок, а сообщение обычно длиннее

AES — блочный шифр. Независимо от длины ключа его блок содержит 16 байтов. Реальное письмо, фотография или запись базы обычно больше одного блока. Поэтому нужен **режим**: правило применения шифра к последовательности данных. Фраза «используем AES» не отвечает на вопросы о повторениях, IV, проверке подмены и управлении ключами.

Представь печать, которая преобразует одну карточку фиксированного размера. Обработать целую стопку можно разными способами: независимо, связывая каждую карточку с предыдущей или создавая отдельную последовательность масок. Это помогает отличить инструмент от порядка применения. Но реальное шифрование не является механической печатью: его гарантии опираются на точные математические условия.

## ECB, CBC и CTR без смешения понятий

В **ECB** одинаковый блок открытого текста под одним ключом даёт одинаковый блок шифротекста. Если в данных много повторений, структура частично видна. Это не означает, что наблюдатель сразу прочитает каждый байт, но уже нарушает требование скрывать закономерности сообщения. ECB не выбирают для обычного шифрования файлов и сообщений.

В **CBC** очередной блок зависит от предыдущего шифротекста, а первый — от IV. Для CBC IV должен удовлетворять требованиям непредсказуемости; он обычно передаётся вместе с сообщением и не является секретным ключом. Сообщение должно соответствовать размеру блока или получить корректное дополнение. CBC само по себе не подтверждает подлинность: обработка ошибок дополнения и комбинирование с MAC требуют осторожности.

В **CTR** шифруется последовательность счётчиков, образуя поток, который соединяют с сообщением через XOR. Один и тот же поток нельзя использовать для двух сообщений. В API библиотеки здесь передаётся 16-байтное начальное значение счётчика. Нужно организовать его уникальность и не допускать пересечения использованных блоков под ключом. Размер ключа не исправляет повтор потока.

**XOR**, или исключающее ИЛИ, работает по битам: одинаковые биты дают 0, разные — 1. Повторное применение той же маски восстанавливает исходное значение. Это свойство делает повтор потока опасным: при XOR двух шифротекстов одна и та же маска сокращается.

## Практика: три наблюдения на настоящем AES

Сохрани в `lab.py`:

```python
import secrets
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

key = secrets.token_bytes(32)
plain = b"0123456789ABCDEF" * 2

def encrypt(mode, data):
    operation = Cipher(algorithms.AES(key), mode).encryptor()
    return operation.update(data) + operation.finalize()

ecb = encrypt(modes.ECB(), plain)
cbc = encrypt(modes.CBC(secrets.token_bytes(16)), plain)
print("ecb_repeated_blocks=", ecb[:16] == ecb[16:])
print("cbc_repeated_blocks=", cbc[:16] == cbc[16:])

def xor(a, b):
    assert len(a) == len(b)
    return bytes(x ^ y for x, y in zip(a, b))

p1 = b"amount=0100;to=A"
p2 = b"amount=0900;to=B"
reused_counter = bytes(16)  # Intentional error for this local demonstration.
c1 = encrypt(modes.CTR(reused_counter), p1)
c2 = encrypt(modes.CTR(reused_counter), p2)
print("cipher_xor=", xor(c1, c2).hex())
print("plain_xor=", xor(p1, p2).hex())
print("same_xor=", xor(c1, c2) == xor(p1, p2))
```

Запусти **`.venv/bin/python lab.py`**. Ожидается `ecb_repeated_blocks= True`, `cbc_repeated_blocks= False`, а две шестнадцатеричные строки XOR должны совпасть. Последняя проверка даст True. Ключ каждый запуск новый, но соотношения сохраняются: они следуют из режима, а не из конкретного случайного ключа.

`b"..."` создаёт байты, `* 2` повторяет 16-байтный блок. Срез `[:16]` выбирает первый блок, `[16:]` — оставшийся. В CBC мы подали ровно два блока, поэтому дополнительное выравнивание здесь не нужно. `encryptor` создаёт отдельную операцию, `update` обрабатывает данные, `finalize` завершает её. Мы не печатаем действующие ключи и не шифруем настоящие пользовательские сведения.

Вторая часть **намеренно нарушает** правило CTR: один ключ и один начальный счётчик применены повторно. `zip` сопоставляет пары байтов, а `assert` не позволяет молча обрезать разные длины. Равенство XOR раскрывает отношение между исходными текстами. Если одно сообщение известно, можно восстановить соответствующий участок второго. Без дополнительных сведений оно не обязательно раскрывает оба сообщения целиком.

## Что изменить для самостоятельной проверки

Поменяй один символ только во втором 16-байтном блоке `plain`, сохранив общую длину. У ECB сравнение должно стать False: одинаковость показывала именно повтор одинаковых блоков, а не «ECB всегда одинаковый». Затем верни исходную строку.

Для CTR создай отдельный случайный начальный счётчик у второй операции и повтори сравнение. Равенство XOR обычно исчезнет. Это иллюстрирует конкретное нарушение, но не доказывает правильную уникальность счётчиков во всей большой системе. В рабочем сервисе учитывают перезапуски, несколько процессов, объём данных и хранение состояния.

Если видишь `ModuleNotFoundError`, проверь, что запускаешь `.venv/bin/python`, а не системный `python3`. Ошибка о длине данных в CBC означает, что ты сделал текст не кратным 16 байтам. Не «лечи» её произвольным удалением последних байтов: для настоящих сообщений используют корректную схему дополнения либо подходящий режим.

## Почему следующий шаг — AEAD

Скрыть содержимое и обнаружить подмену — разные задачи. ECB, CBC и CTR в показанном виде не дают аутентификации сообщения. Для прикладного кода обычно выбирают проверенную схему AEAD через высокоуровневый API и соблюдают её требования к nonce и ключу. В день 73 мы отдельно проверим тег AES-GCM, отказ при изменении данных и роль TLS. Настоящие криптографические протоколы не собирают из этих учебных фрагментов.

Тематическая основа — Block Ciphers и Stream Ciphers из Serious Cryptography. Программы написаны для Kairon, правила API сверяются с документацией cryptography. Смысл опыта — увидеть конкретные свойства и ограничения режимов, а не получить готовый шифратор личных файлов.
