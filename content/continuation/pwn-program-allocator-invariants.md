## Перед началом: Как работает динамическая память (Heap) и почему опасно хранить старый ключ от номера

Если стек автоматически выделяет и освобождает память при входе в функцию и выходе из неё, то для объектов, которые должны жить долго или менять размер во время работы программы, используется **динамическая память — куча (heap)** и функции `malloc` / `free` (в C) или `new` / `delete` (в C++).

В курсе **Program Security** (`Dynamic Allocator Misuse`) и в курсе **Software Exploitation** (`Dynamic Allocator Exploitation`) на `pwn.college` подробно разбирают, как устроен распределитель памяти (аллокатор `ptmalloc` в `glibc`, его быстрый кэш `tcache`) и к чему приводят две классические ошибки работы с указателями: **обращение после освобождения (`Use-After-Free`, UAF)** и **повторное освобождение (`Double Free`)**.

Представь гостиницу, где администратор ведёт список свободных номеров.
1. Гость А заселился в номер 101 (`malloc`), получил ключ-карту (указатель `ptr_a`), а вечером выписался (`free(ptr_a)`), но **оставил дубликат ключа у себя в кармане** (программа не обнулила переменную `ptr_a = NULL`).
2. Администратор положил номер 101 на самый верх стопки освободившихся комнат (**LIFO-список свободных блоков `tcache`**) и тут же заселил в этот же номер 101 нового гостя Б (`ptr_b = malloc(...)`)!
3. Теперь и старый ключ гостя А (`ptr_a`), и новый ключ гостя Б (`ptr_b`) открывают **одну и ту же комнату 101**! Если гость А по старой памяти изменит вещи в комнате (`Use-After-Free`), он перезапишет данные нового гостя Б. А если гость А сдаст свой ключ на стойку во второй раз (`Double Free`), номер 101 попадёт в список свободных дважды подряд, и администратор заселит в одну комнату сразу двух новых разных гостей.

## Почему это работает: Список свободных блоков tcache, UAF и Double Free

Разберём три правила работы аллокатора кучи:

1. **Быстрое переиспользование блоков того же размера (`tcache` LIFO)**. Чтобы не просить память у ядра при каждом мелком вызове `malloc`, распределитель хранит освобождённые блоки (чанки, *chunks*) в односвязных списках по размерам (корзинах `tcache bins`). Блок, освобождённый последним через `free(p)`, кладётся в голову списка и выдаётся **первым же** при следующем запросе `malloc` того же размера.
2. **Висячий указатель (Dangling Pointer) и Use-After-Free (UAF)**. Вызов `free(p)` возвращает блок памяти аллокатору, но **не меняет саму переменную `p`**, в которой хранился адрес этого блока. Такой указатель называют «висячим». Если после этого создать в том же размере новую структуру (например, объект с правами доступа), она получит тот же самый адрес, и запись или чтение через старый указатель `p` обратится к полям нового объекта.
3. **Повторное освобождение (`Double Free`) и защита инвариантов**. Когда блок свободен, аллокатор хранит прямо внутри первых байтов этого блока служебный указатель `next` (или `fd` — *forward pointer*) на следующий свободный блок в списке. Если один и тот же адрес `p` попадёт в список свободных дважды без проверки, в списке образуется петля, и два последовательных вызова `malloc` вернут одинаковый адрес для двух независимых объектов. Современные версии `glibc` проверяют специальное поле `key` в освобождённом чанке `tcache`, чтобы обнаруживать повторный `free`, а в коде программы переменную указателя сразу после освобождения обнуляют (`p = NULL`).

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
class SimpleAllocator:
    def __init__(self):
        self.next_addr = 0x602000
        self.tcache_free = []
        self.memory = {}

    def malloc(self, initial_data):
        if self.tcache_free:
            addr = self.tcache_free.pop()
        else:
            addr = self.next_addr
            self.next_addr += 0x20
        self.memory[addr] = dict(initial_data)
        return addr

    def free(self, addr, check_double_free=True):
        if check_double_free and addr in self.tcache_free:
            return "aborted:double_free_detected"
        self.tcache_free.append(addr)
        return "freed:ok"


heap = SimpleAllocator()
user_note_ptr = heap.malloc({"kind": "note", "role": "guest"})
first_free = heap.free(user_note_ptr)
double_free = heap.free(user_note_ptr, check_double_free=True)

session_ptr = heap.malloc({"kind": "session", "role": "viewer"})
reused_same_chunk = user_note_ptr == session_ptr

# Ошибка UAF: запись через старый не обнулённый указатель user_note_ptr
heap.memory[user_note_ptr]["role"] = "overwritten-via-uaf"
print("first_free=", first_free, "double_free=", double_free)
print("reused_same_chunk=", reused_same_chunk, "addr=", hex(session_ptr))
print("session_role_after_uaf=", heap.memory[session_ptr]["role"])
```

### Шаг 2. Запусти программу и разбери каждое наблюдение

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**


Посмотри, как цепочка событий видна как на ладони:
- первый вызов `heap.malloc` выделил чанк по адресу `0x602000` для заметки `user_note_ptr`;
- после `heap.free(user_note_ptr)` адрес `0x602000` попал в список `tcache_free`. Попытка освободить его второй раз подряд с включённой проверкой `check_double_free=True` была остановлена (`aborted:double_free_detected`);
- следующий вызов `heap.malloc` для совершенно другого объекта (`session_ptr`) взял свободный чанк из верхушки `tcache_free` и получил **тот же самый адрес `0x602000`** (`reused_same_chunk= True`);
- поскольку старый указатель `user_note_ptr` не был сброшен в `None`, обращение через него изменило поле `"role"` внутри нового объекта `session_ptr` на `"overwritten-via-uaf"`.

### Шаг 3. Проверь, как обнуление указателя предотвращает UAF

В файле `lab.py` посмотри, что изменится, если перед созданием `session_ptr` явно сбросить старый указатель или проверить, что мы не пишем по устаревшей ссылке: замени строку `heap.memory[user_note_ptr]["role"] = "overwritten-via-uaf"` на условную проверку `if user_note_ptr is None: heap.memory[session_ptr]["role"] = "overwritten"`, сохрани и запусти `python3 lab.py`. Теперь `session_role_after_uaf=` сохранит исходное значение `viewer`. После проверки верни строку обратно, чтобы тест моделировал исходный случай.

## Почему это работает: Как защищают работу с кучей в современных программах

В задачах **Program Security** на `pwn.college` и при ревью кода на C/C++ проверяют три вещи:
1. **Обнуление указателя сразу после `free(ptr)`**: присваивание `ptr = NULL` гарантирует, что любое повторное использование этого указателя приведёт к немедленному и предсказуемому отказу при обращении к нулевому адресу, а `free(NULL)` по стандарту языка C является безопасной пустой операцией.
2. **Единовременное владение памятью**: в современном C++ (`std::unique_ptr`) и в языке Rust компилятор на этапе сборки запрещает использовать переменную после того, как владение памятью было передано или объект был освобождён.
3. **Инструмент динамической проверки AddressSanitizer (`-fsanitize=address`, ASan)**: при тестировании программ в Kali компиляция с флагом `-fsanitize=address` помещает освобождённые блоки в карантин и мгновенно печатает точный стек вызовов при первой же попытке `heap-use-after-free` или `double-free`.

## Если не получилось: Частые ошибки

- **Почему в реальной программе `malloc` не всегда возвращает только что освобождённый адрес**: переиспользование срабатывает тогда, когда размер нового запроса попадает в ту же корзину размера (`bin` / `tcache`), куда вернулся освобождённый чанк.
- **Смешивание понятий утечки памяти (`memory leak`) и `Use-After-Free`**: если забыть вызвать `free`, память просто останется занятой (утечка памяти). А `Use-After-Free` возникает наоборот — когда `free` уже вызвали, но программа продолжает читать или писать по старому адресу.
