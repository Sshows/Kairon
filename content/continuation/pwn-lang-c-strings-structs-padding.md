## Перед началом: Почему строка без нулевого байта читает чужие секреты, а внутри `struct` прячутся «пустые» байты памяти

В модулях **Arrays and C-Strings**, **Pointers** и **Structures** практикума **Intro to Programming Languages** (`pwn.college`) разбирают две ловушки языка C, из-за которых программы нечаянно отправляют по сети куски собственной оперативной памяти (**Information Disclosure / Uninitialized Memory Leak**):
1. как устроена классическая **нуль-терминированная строка C (`C-string`)** и что происходит, когда функция `strncpy` или `read` заполняет буфер вплотную без завершающего байта `\x00`;
2. почему компилятор вставляет между полями структуры `struct` невидимые байты выравнивания (**Structure Padding**) и почему копирование структуры через `write(fd, &pkt, sizeof(pkt))` без предварительного обнуления сливает старые данные со стека или из кучи.

Представь два бытовых примера. В первом примере диктор на вокзале читает объявление с бумажной ленты: по правилам он читает все буквы подряд, пока не встретит красную точку остановки (нулевой байт `\x00`). Если сотрудник приклеил новую полоску текста ровно на 8 букв поверх старой ленты, но забыл поставить в конце красную точку, диктор без паузы прочитает и все 8 новых букв, и старый секретный текст, который шёл следом на ленте!

Во втором примере ты упаковываешь приборы в стандартный ящик с ячейками (`struct`). Между маленьким 1-байтовым датчиком (`uint8_t type`) и длинной 8-байтовой трубкой (`uint64_t id`) в ящике остаётся 7 пустых отсеков для ровной укладки (**7 байт padding**). Если ящик взяли со старого склада, где в этих отсеках остался лежать чужой черновик, и отправили ящик целиком (`sizeof(struct)` = 16 байт), получатель увидит все 7 байт старого черновика!

## Почему это работает: Нулевой терминатор `\x00`, функция `strlen` и выравнивание полей `struct`

Разберём устройство строк и структур C на уровне байтов памяти:

1. **Строка в C (`char *`) не хранит свою длину числом**. В отличие от `str` в Python или `String` в Rust (где длина хранится в отдельном поле), строка в C — это просто адрес первого символа, а конец строки отмечается первым встреченным байтом со значением `0x00` (`'\0'`). Функция `strlen(ptr)` или `printf("%s", ptr)` шагает по байтам `ptr[0], ptr[1], ...` до тех пор, пока не встретит `0x00`.
2. **Ловушка `strncpy(dst, src, N)` и чтения фиксированного размера**. Если буфер `char name[8]` лежит в памяти вплотную перед массивом `char token[8]`, и в `name` записали ровно 8 букв `'A'` без нулевого байта на конце, то в `name` нет `0x00`. Любой вызов `printf("%s", name)` или `puts(name)` прочитает сначала все 8 букв `'A'`, а затем без остановки продолжит печатать байты `token` до первого случайного `0x00`! Чтобы этого не происходило, в буфере размера `N` под текст оставляют `N - 1` байт и принудительно записывают `name[N - 1] = '\0'`.
3. **Выравнивание полей структуры (`Struct Alignment & Padding`)**:
   - процессор быстрее всего читает 4-байтовое число (`uint32_t`) с адреса, кратного `4`, а 8-байтовое число (`uint64_t`) — с адреса, кратного `8`;
   - поэтому в структуре `struct Packet { uint8_t tag; uint64_t seq; };` поле `tag` занимает смещение `0` (1 байт), затем компилятор автоматически оставляет **7 байт пустого промежутка (padding)** на смещениях `1..7`, а поле `seq` кладёт со смещения `8..15`. Общий размер `sizeof(struct Packet)` оказывается равен **16 байтам**, а не 9!
4. **Почему присваивание полей `pkt.tag = 1; pkt.seq = 42;` не очищает `padding`**. Когда структура создаётся на стеке, компилятор записывает только сами именованные поля (`tag` и `seq`), а 7 байт промежутка `1..7` сохраняют тот «мусор» (например, части старых ключей или указателей со стека), который лежал на этом месте раньше. Поэтому перед заполнением структуры для отправки по сети или записи в файл всю её область памяти обязательно обнуляют: `memset(&pkt, 0, sizeof(pkt))` или инициализируют нулями `struct Packet pkt = {0};`.

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
def c_Side_by_side_strlen_read(adj_memory):
    nul_pos = adj_memory.find(b"\x00")
    if nul_pos == -1:
        return adj_memory.decode("ascii", errors="replace")
    return adj_memory[:nul_pos].decode("ascii", errors="replace")


def write_c_string(buf_8_plus_secret, user_bytes, force_null=False):
    mem = bytearray(buf_8_plus_secret)
    if force_null:
        clipped = user_bytes[:7]
        mem[0 : len(clipped)] = clipped
        mem[len(clipped)] = 0
    else:
        clipped = user_bytes[:8]
        mem[0 : len(clipped)] = clipped
    return c_Side_by_side_strlen_read(bytes(mem))


def pack_struct_packet(stack_frame_16, tag_u8, seq_u64, zero_init=False):
    raw = bytearray(16) if zero_init else bytearray(stack_frame_16)
    raw[0] = tag_u8 & 0xFF
    raw[8:16] = seq_u64.to_bytes(8, "little")
    leaked_padding = bytes(raw[1:8])
    return bytes(raw), leaked_padding


initial_mem = b"guest\x00\x00\x00" + b"KEY-991\x00"
dirty_stack = b"\xff" + b"OLD_KEY" + (0).to_bytes(8, "little")

unterminated_out = write_c_string(initial_mem, b"AAAAAAAA", force_null=False)
terminated_out = write_c_string(initial_mem, b"AAAAAAAA", force_null=True)

_, pad_dirty = pack_struct_packet(dirty_stack, tag_u8=1, seq_u64=100, zero_init=False)
_, pad_clean = pack_struct_packet(dirty_stack, tag_u8=1, seq_u64=100, zero_init=True)

print("unterminated_puts=", unterminated_out)
print("safe_terminated_puts=", terminated_out)
print("uninitialized_padding=", pad_dirty, "zeroed_padding=", pad_clean.hex())
```

### Шаг 2. Запусти программу и сравни вывод

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text

safe_terminated_puts= AAAAAAA
uninitialized_padding= b'OLD_KEY' zeroed_padding= 00000000000000
```

Разберём оба эффекта:
- в `unterminated_out` запись 8 байт `b"AAAAAAAA"` в 8-байтовый буфер затёрла все нулевые байты перед соседним полем `KEY-991\x00`, поэтому чтение до первого `\x00` (`puts` / `printf("%s")`) слило в ответ оба буфера подряд: `AAAAAAAAKEY-991`;
- в `safe_terminated_puts` (`force_null=True`) под полезные символы оставлено 7 байт, а в 8-й байт гарантированно записан `\x00`, поэтому чтение остановилось ровно на границе буфера (`AAAAAAA`);
- в `pack_struct_packet` при `zero_init=False` запись полей `tag` (байт `0`) и `seq` (байты `8..15`) не тронула 7 байт выравнивания (`raw[1:8]`), и в сетевой пакет утекли старые байты со стека `b'OLD_KEY'`. Предварительное обнуление структуры (`zero_init=True`, аналог `memset(&pkt, 0, sizeof(pkt))`) полностью очистило промежуток (`00000000000000`).

## Почему это работает: Как компиляторы и анализаторы предотвращают утечки памяти структур

В современном ядре Linux и защищённых проектах C/C++ используют флаг компилятора **`-ftrivial-auto-var-init=zero`**, который заставляет компилятор автоматически заполнять нулями все новые переменные и структуры на стеке (включая их скрытые байты `padding`) прямо при входе в функцию.

## Если не получилось: Частые ошибки

- **Доверие функции `strncpy(dst, src, sizeof(dst))`**: вопреки названию, стандартная функция `strncpy` **не ставит** завершающий `\0`, если длина `src` больше или равна `sizeof(dst)`. Безопаснее использовать `snprintf(dst, sizeof(dst), "%s", src)`, которая всегда гарантирует нулевой терминатор в конце буфера.
