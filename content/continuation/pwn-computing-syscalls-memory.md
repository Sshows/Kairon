## Перед началом: Как программа разговаривает с ядром и хранит числа в памяти

Когда программа на C, Rust или Python хочет прочитать файл, вывести строку на экран или завершиться с кодом ответа, она не может сама напрямую обратиться к диску или монитору. Между обычной программой (режим пользователя, *user space*) и оборудованием стоит **ядро операционной системы** (*kernel space*).

Представь закрытое хранилище банка: клиент не заходит в сейф сам, а заполняет бланк строго по форме в окошке операциониста — указывает номер услуги в первой графе и параметры в следующих графах, после чего нажимает кнопку вызова. В процессоре x86-64 такой бланк состоит из **регистров**, а кнопка вызова называется инструкцией **`syscall`** (системный вызов).

В курсе **Computing 101** на `pwn.college` (модули `Your First Program`, `Introspecting`, `Memory` и `Assembly Crash Course`, открытая лицензия BSD-2-Clause) ученик собирает первые программы из нескольких инструкций и следит за ними через трассировщик системных вызовов `strace`. Сегодня мы разберём две главные вещи, без которых чтение памяти и дампов кажется набором случайных букв: **таблицу регистров системного вызова Linux x86-64** и порядок байтов **little-endian**.

## Почему это работает: Регистры syscall в x86-64 и порядок байтов little-endian

Разберём устройство вызова и памяти простыми словами:

1. **Какие регистры передают системный вызов в Linux x86-64**:
   - **`rax`** — номер самой услуги (системного вызова). Например, в Linux x86-64: `0` — `read` (прочитать байты), `1` — `write` (записать байты), `2` — `open` (открыть файл), `60` — `exit` (завершить процесс). После выполнения `syscall` ядро кладёт ответ (сколько байт прочитано/записано или отрицательный код ошибки) обратно в тот же регистр **`rax`**.
   - **`rdi`** — первый аргумент (например, для `write` это номер файлового дескриптора: `1` для экрана `stdout`; для `exit` — код возврата процесса).
   - **`rsi`** — второй аргумент (для `write` — адрес в памяти, где начинается текст).
   - **`rdx`** — третий аргумент (для `write` — сколько байт нужно вывести).
2. **Почему числа и адреса в памяти записаны «задом наперёд» (little-endian)**. Мы привыкли писать числа слева направо от старшего разряда к младшему: в шестнадцатеричном числе `0x01020304` самый старший байт — `01`, а самый младший — `04`. Но архитектура x86 и x86-64 хранит многобайтовые числа в памяти по правилу **little-endian** («младший байт по младшему адресу»): по первому адресу ложится байт `04`, затем `03`, `02` и `01`. При этом **обычная текстовая строка** (массив отдельных однобайтовых символов, например `"KALI"`) всегда лежит в памяти по порядку букв: `'K'`, `'A'`, `'L'`, `'I'`. Перепутать порядок байтов числа и порядок символов строки — самая частая ошибка при чтении дампов памяти.

## Сделай сейчас: Практика: проверь порядок байтов little-endian и модель системных вызовов

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой окно редактора:

```python
value = 0x1122334455667788
little = value.to_bytes(8, byteorder="little")
big = value.to_bytes(8, byteorder="big")
print("little_hex=", little.hex())
print("first_little_byte=", hex(little[0]), "last_little_byte=", hex(little[-1]))
print("round_trip=", int.from_bytes(little, byteorder="little") == value)
print("big_ differs=", little != big)


def run_syscall(rax, rdi, rsi, rdx, memory):
    if rax == 1:  # sys_write(fd=rdi, buf=rsi, count=rdx)
        if rdi not in (1, 2) or rsi < 0 or rdx < 0 or rsi + rdx > len(memory):
            return -14, b""
        chunk = bytes(memory[rsi : rsi + rdx])
        return len(chunk), chunk
    if rax == 60:  # sys_exit(status=rdi)
        return rdi & 0xFF, b""
    return -38, b""


mem = bytearray(b"HEADER:pwn-college-ok:FOOTER")
ret_write, out_bytes = run_syscall(rax=1, rdi=1, rsi=7, rdx=14, memory=mem)
ret_exit, _ = run_syscall(rax=60, rdi=42, rsi=0, rdx=0, memory=mem)
print("sys_write_ret=", ret_write, "text=", out_bytes.decode("ascii"))
print("sys_exit_code=", ret_exit)
```

### Шаг 2. Запусти программу и сверь вывод

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
little_hex= 8877665544332211
first_little_byte= 0x88 last_little_byte= 0x11
round_trip= True
big_ differs= True
sys_write_ret= 14 text= pwn-college-ok
sys_exit_code= 42
```

Обрати внимание на первые строки:
- у 8-байтового числа `0x1122334455667788` самый младший байт равен `0x88`. Поэтому в представлении `little-endian` (`little_hex=`) он стоит самым первым (`8877665544332211`), и `little[0]` равен `0x88`;
- во второй части вызов `run_syscall(rax=1, rdi=1, rsi=7, rdx=14, ...)` повторяет логику системного вызова `write(1, buf+7, 14)`: он берёт ровно 14 байт начиная со смещения `7` (пропуская `HEADER:`) и возвращает длину `14` в `rax` и срез `pwn-college-ok`.

### Шаг 3. Измени длину среза и посмотри на настоящий системный вызов в Kali

В файле `lab.py` измени `rdx=14` на `rdx=3` в вызове `run_syscall(rax=1, ...)`, сохрани файл и запусти `python3 lab.py`. Теперь программа выведет `sys_write_ret= 3 text= pwn`, потому что регистр `rdx` ограничивает число передаваемых байт независимо от того, что лежит в памяти дальше. Верни `rdx=14` обратно и снова проверь вывод.

Если в твоей Kali установлена утилита `strace`, можешь увидеть настоящие системные вызовы `write` и `exit_group` одной командой в терминале:

```bash
strace -e trace=write,exit_group python3 -c "print('hello-syscall')"
```

В выводе ты увидишь строку `write(1, "hello-syscall\n", 14) = 14` и `exit_group(0) = ?` — это те же самые аргументы (`rdi=1`, буфер `rsi`, длина `rdx=14` и возврат `14`), которые мы разобрали в модели.

## Почему это работает: Как это применяется в Computing 101 и отладке

В модулях `Introspecting` и `Debugging Refresher` курса **Computing 101** на `pwn.college` анализ любой неизвестной программы начинается с наблюдения за её границей с ядром:
- утилита `strace` показывает все системные вызовы и их аргументы без необходимости дизассемблировать весь бинарный файл: какие файлы программа пытается открыть (`openat`), что пишет (`write`) и какой код возврата передаёт при выходе (`exit` / `exit_group`);
- при осмотре памяти в отладчике GDB важно помнить, читаешь ли ты массив байтов (`x/16bx`) или 8-байтовое целое число (`x/gx`), которое GDB сам собирает из `little-endian` байтов в привычный вид.

## Если не получилось: Частые ошибки

- **Перепутаны байты и шестнадцатеричные цифры**: один байт записывается **двумя** шестнадцатеричными цифрами (например, `88` или `11`). Поэтому при развороте `little-endian` пары цифр не переворачиваются внутри себя: `0x1234` в памяти по байтам выглядит как `34 12`, а не `43 21`.
- **Отрицательное число в возврате системного вызова (`-14`, `-2`)**: ядро Linux возвращает коды ошибок (`-ENOENT`, `-EFAULT`) как отрицательные числа в регистре `rax`.
