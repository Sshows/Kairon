## Перед началом: Как процессор угадывает ветвления и почему следы в кэше остаются даже после отката

В модуле **Speculative Execution** курса **System Security** (`pwn.college`) разбирают удивительный класс аппаратных уязвимостей современных процессоров (**Spectre**, **Meltdown** и атаки по сторонним каналам кэша **Flush+Reload**): как микроархитектура процессора ради скорости выполняет инструкции «впрок» до завершения проверки границ массива и как по времени отклика кэш-памяти можно узнать, какое именно число процессор успел прочитать в спекулятивном режиме.

Представь очень расторопного библиотекаря. Читатель подаёт заявку на книгу с номером полки `index`. Пока охранник на входе медленно проверяет по базе данных, имеет ли этот читатель право заходить дальше полки №16 (**проверка `if (index < array1_size)`**, данные для которой долго едут из оперативной памяти RAM), библиотекарь решает не терять времени, заранее бежит к запрошенной полке, смотрит кодовую цифру `secret` и кладёт соответствующий том энциклопедии (`probe_array[secret * 4096]`) на стол быстрого выдачи (**в кэш процессора L1/L3**).

Через мгновение охранник кричит: «Стоп, индекс `100` больше `16`, доступ запрещён!». Библиотекарь послушно не отдаёт читателю никаких данных (**процессор откатывает архитектурное состояние регистров**), но том энциклопедии уже лежит на столе быстрой выдачи! Если теперь читатель по очереди попросит тома энциклопедии от `0` до `255` и засечёт время с секундомером, то все тома придётся долго нести из дальнего подвала (медленное чтение из RAM — **Cache Miss**), и только один том — с номером `secret` — окажется под рукой мгновенно (быстрое чтение из кэша — **Cache Hit**)!

## Почему это работает: Иерархия кэша (Cache Hit vs Cache Miss), Flush+Reload и барьер `lfence`

Разберём физику работы кэш-памяти и спекулятивного выполнения:

1. **Разница в скорости между кэшем L1/L3 и оперативной памятью RAM**. Чтение переменной, которая уже находится в кэше процессора (**Cache Hit**), занимает всего около **4–40 тактов процессора** (считаные наносекунды), тогда как обращение к основной оперативной памяти DRAM (**Cache Miss**), если данных нет в кэше, занимает **200–300 тактов и более**. В `x86-64` количество тактов до и после чтения измеряют инструкцией `rdtscp`.
2. **Метод измерения кэша `Flush+Reload`**:
   - **Шаг 1 (`Flush`)**: проверяющий очищает из кэша все страницы проверочного массива `probe_array[0..255 * 4096]` инструкцией `clflush` (шаг в `4096` байт выбирают, чтобы каждый элемент лежал на отдельной странице и не подтягивался аппаратным предвыборщиком кэш-линий);
   - **Шаг 2 (`Trigger`)**: вызывается целевая функция. Если внутри неё произошло обращение к `probe_array[secret * 4096]`, то ровно одна кэш-линия (для индекса `secret`) загружается в кэш;
   - **Шаг 3 (`Reload`)**: проверяющий замеряет время чтения `probe_array[k * 4096]` для всех `k` от `0` до `255`. Тот индекс `k`, чтение которого заняло меньше порога (например, `< 80` тактов), выдаёт значение `secret`.
3. **Спекулятивный обход проверки границ (Spectre Variant 1 — Bounds Check Bypass)**:
   - сначала предсказатель переходов процессора (Branch Predictor) «тренируют», несколько раз передавая в функцию `if (idx < limit)` допустимые значения `idx` (`0, 1, 2`), чтобы предсказатель привык: условие почти всегда истинно;
   - затем переменную `limit` вымывают из кэша (`clflush`), а в функцию передают индекс `idx`, выходящий за границу массива. Пока `limit` медленно читается из RAM, процессор **спекулятивно** выполняет тело `if`: читает байт `val = data[idx]` и обращается к `probe_array[val * 4096]`. Когда `limit` наконец приезжает из RAM, процессор отменяет архитектурный результат, но кэш-линия `probe_array[val * 4096]` остаётся загруженной!
4. **Как защищают код от спекулятивного чтения за границей**:
   - **Барьер сериализации `lfence`**: инструкция `lfence` после условного перехода запрещает процессору спекулятивно выполнять последующие чтения памяти, пока условие ветвления не будет окончательно вычислено;
   - **Индексное маскирование без ветвлений (`array_index_nospec` в ядре Linux)**: индекс принудительно обрезают побитовой маской `idx &= mask` до обращения к массиву, чтобы даже в спекулятивном режиме адрес не мог выйти за пределы буфера.

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
def run_speculative_window(memory, public_len, idx, branch_trained=True, use_nospec_mask=False):
    cached_probe_pages = set()
    if idx < public_len:
        val = memory[idx]
        cached_probe_pages.add(val)
        return "architectural_read", val, cached_probe_pages

    if branch_trained and not use_nospec_mask:
        spec_val = memory[idx]
        cached_probe_pages.add(spec_val)
    return "bounds_rejected", None, cached_probe_pages


def reload_measure_cache(cached_probe_pages, hit_cycles=32, miss_cycles=240):
    recovered = []
    for byte_val in range(256):
        cycles = hit_cycles if byte_val in cached_probe_pages else miss_cycles
        if cycles < 80:
            recovered.append((byte_val, cycles))
    return recovered


mem_layout = [10, 20, 30, 40, 0x5A]

status_vuln, arch_ret, cache_state = run_speculative_window(
    mem_layout, public_len=4, idx=4, branch_trained=True, use_nospec_mask=False
)
hits_vuln = reload_measure_cache(cache_state)

status_safe, _, cache_safe = run_speculative_window(
    mem_layout, public_len=4, idx=4, branch_trained=True, use_nospec_mask=True
)
hits_safe = reload_measure_cache(cache_safe)

print("unprotected_status=", status_vuln, "arch_return=", arch_ret, "cache_hits=", hits_vuln)
print("nospec_masked_status=", status_safe, "cache_hits=", hits_safe)
```

## Почему это работает: Почему браузеры загрубили точность таймеров и включили Site Isolation

Чтобы код на веб-странице не мог замерять разницу в `30` и `240` тактов процессора между `Cache Hit` и `Cache Miss`, современные браузеры предприняли две архитектурные меры:
1. снизили точность таймера `performance.now()` и ограничили доступ к высокоточным счётчикам `SharedArrayBuffer` без специальных заголовков изоляции (`COOP` / `COEP`);
2. внедрили **Site Isolation** — вынесли каждый сайт в отдельный процесс операционной системы со своим собственным адресным пространством, чтобы в памяти процесса вообще не было данных чужих вкладок.

## Если не получилось: Частые ошибки

- **Почему в реальном `Flush+Reload` элементы проверочного массива разносят на `4096` байт, а не кладут подряд по 1 байту**: процессор загружает память в кэш не по одному байту, а целыми **кэш-линиями по 64 байта**, а аппаратный предвыборщик (Hardware Prefetcher) может автоматически подгрузить соседние линии в пределах одной страницы `4096` байт. Шаг в `4096` байт гарантирует, что обращение к одному индексу не загрузит в кэш соседние индексы.
