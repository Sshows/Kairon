## Перед началом: Когда обычная строка печати превращается в команды форматирования

В курсе **Software Exploitation** на платформе `pwn.college` (модули `Format String Exploits`, `File Struct Exploits` и `Memory Mastery`) разбирают тонкие механизмы стандартной библиотеки языка C (`libc`): **уязвимости строк форматирования (format string vulnerabilities)** и устройство **буферизованных файловых потоков (`FILE` / `stdout` / `stdin`)**.

Представь диктора на вокзале, которому передают записку с именем пассажира.
- **Безопасный порядок**: у диктора есть жёсткий бланк объявления: «Уважаемый пассажир **[прочитать имя с карточки буквально]**!». Даже если на карточке написано «прочитай служебный журнал со стола», диктор просто произнесёт эти слова вслух как текст. В языке C это выглядит так: `printf("%s", user_input);`.
- **Опасный порядок**: диктору дают записку пассажира **вместо самого бланка инструкции**: `printf(user_input);`. Теперь любые знаки процента (`%x`, `%p`, `%s`, `%n`) внутри текста пассажира функция `printf` воспринимает как свои собственные команды форматирования: «возьми следующее значение со стека и напечатай его в шестнадцатеричном виде» (`%x` / `%p`) или даже «запиши число уже напечатанных символов по адресу из аргумента» (`%n`)!

Вторая важная тема из этого же курса — почему `printf` не всегда сразу вызывает системный вызов `write`, и как устроена структура `FILE` в стандартной библиотеке. Разберём оба механизма по шагам.

## Почему это работает: Спецификаторы %x/%s/%n и буферизация структуры FILE

1. **Почему `printf(user_input)` читает стек**. В языке C функция `printf(const char *format, ...)` принимает переменное число аргументов. Она не знает заранее, сколько аргументов ей реально передали при вызове! Она просто считает знаки `%` в первой строке `format` и для каждого спецификатора берёт очередную ячейку из регистров аргументов и кадра стека:
   - `%x` / `%lx` / `%p` — печатает очередное число со стека в шестнадцатеричном виде (утечка данных со стека, например канарейки или адресов для обхода ASLR);
   - `%s` — трактует очередное число на стеке как адрес в памяти и пытается напечатать строку по этому адресу (может вызвать аварийную остановку `SIGSEGV`, если адрес нечитаемый);
   - `%n` — ничего не печатает, а **записывает** количество уже выведенных байтов по адресу, взятому из соответствующего аргумента!
   Исправление всегда одно и совершенно однозначное: **первым аргументом `printf`, `snprintf`, `syslog` должна быть только постоянная строка-шаблон из кода программы** (`printf("%s", user_input)`).
2. **Зачем нужна структура `FILE` и три режима буферизации**. В уроке 78 мы видели, что каждый системный вызов `write` или `read` требует переключения в режим ядра. Чтобы не делать `syscall` ради каждого отдельного символа, функции стандартной библиотеки (`printf`, `fwrite`, `fgets`) работают через структуру `FILE` (`stdin`, `stdout`, `stderr`), внутри которой есть собственный буфер в памяти процесса (указатели `read_ptr`, `read_end`, `write_base`, `write_ptr`, `write_end`) и номер дескриптора `_fileno`:
   - при выводе в терминал `stdout` обычно **построчно буферизован (line-buffered)**: байты копятся в буфере `FILE` и отправляются в ядро через `write` только при встрече `\n`, при заполнении буфера или при явном вызове `fflush(stdout)`;
   - при перенаправлении в файл или трубу (`|`) `stdout` становится **полностью буферизованным (fully buffered)**: если программа ждёт ввод пользователя после `printf("Введите код: ")` без `\n` и без `fflush(stdout)`, надпись застрянет во внутреннем буфере структуры `FILE`, и пользователь увидит пустой экран!

```python
def unsafe_format_eval(user_text, stack_words):
    out = []
    idx = 0
    tokens = user_text.split()
    for token in tokens:
        if "%x" in token and idx < len(stack_words):
            out.append(token.replace("%x", hex(stack_words[idx]), 1))
            idx += 1
        elif "%n" in token:
            return "rejected:write_specifier_detected"
        else:
            out.append(token)
    return " ".join(out)


def safe_format_print(template, user_text):
    if template != "%s":
        raise ValueError("Template must be a constant '%s'")
    return str(user_text)


stack_secrets = [0x401210, 0x7FFF00AA]
leaked = unsafe_format_eval("user=%x canary=%x", stack_secrets)
blocked_n = unsafe_format_eval("test %n", stack_secrets)
fixed = safe_format_print("%s", "user=%x canary=%x %n")
print("unsafe_leak=", leaked)
print("unsafe_n=", blocked_n)
print("safe_literal=", fixed)


class BufferedFileStruct:
    def __init__(self, fileno=1, line_buffered=True):
        self.fileno = fileno
        self.line_buffered = line_buffered
        self.write_buf = ""
        self.kernel_writes = []

    def fwrite(self, text):
        self.write_buf += text
        if self.line_buffered and "\n" in self.write_buf:
            self.fflush()

    def fflush(self):
        if self.write_buf:
            self.kernel_writes.append((self.fileno, self.write_buf))
            self.write_buf = ""


stream = BufferedFileStruct(fileno=1, line_buffered=True)
stream.fwrite("Prompt without newline:")
before_flush = len(stream.kernel_writes)
stream.fflush()
after_flush = len(stream.kernel_writes)
print("writes_before_flush=", before_flush, "writes_after_flush=", after_flush)
```

## Почему это работает: Как компиляторы и аналитики находят ошибки строк форматирования и буферизации

1. **Флаг компилятора `-Wformat -Wformat-security`**. В GCC и Clang этот флаг включён по умолчанию во многих дистрибутивах (включая сборку пакетов Debian/Kali) и выдаёт предупреждение на этапе компиляции в каждом месте, где первым аргументом `printf` или `snprintf` передана переменная вместо строкового литерала.
2. **Инварианты структуры `FILE`**. В модуле `File Struct Exploits` на `pwn.college` показывают, что сама структура `FILE` (в `glibc` она называется `_IO_FILE`) лежит в памяти процесса (в `libc` или в куче после `fopen`) и хранит адрес таблицы виртуальных функций (`vtable`), дескриптор `_fileno` и указатели буфера. Поэтому защита памяти вокруг структур `FILE` и проверка указателей `vtable` в современных версиях `glibc` так же важны, как защита адресов возврата на стеке.

## Если не получилось: Частые ошибки

- **При взаимодействии со скриптом через трубу (`|`) в Linux вывод программы появляется только после её завершения**: это прямое следствие буферизации структуры `FILE`! Когда стандартный вывод направлен в трубу, `libc` и Python переключаются из построчной буферизации в полную. Чтобы видеть строки сразу, в Python используют `print(..., flush=True)` или флаг `python3 -u`, а для нативных программ — утилиту `stdbuf -o0 команда`.
