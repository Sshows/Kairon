## Перед началом: Почему стойкий алгоритм AES становится уязвимым при неверном режиме работы или слабом генераторе случайных чисел

В официальном сообществе практикумов `pwn.college` — **Cryptographic Exploitation (Cryptomania)** и модуле **Cryptography** курса **Intro to Cybersecurity** — разбирают важнейший урок прикладной криптографии: сам по себе блочный шифр `AES` математически надёжен, но ошибки в его обвязке — режим `AES-ECB`, раскрытие ошибок дополнения `PKCS#7` в `AES-CBC` без проверки подлинности (`MAC`) и использование обычного генератора `random` вместо криптографического `secrets` — позволяют атакующему подделывать токены и восстанавливать данные без знания ключа!

Представь бронированный инкассаторский сейф, который перевозит стандартные коробки ровно по 16 килограммов (16-байтовые блоки `AES`). Если на каждую коробку с одинаковым содержимым клеить абсолютно одинаковый штрихкод (**режим `ECB` — Electronic Codebook**) и не опечатывать всю партию целиком общей пломбой (**отсутствие `HMAC` / `AEAD`**), то злоумышленник по дороге может поменять коробки местами или заменить коробку `role=guest      ` на ранее скопированную коробку `role=admin      `! А если при распаковке в режиме `CBC` приёмщик громко кричит в коридор: «Коробка распечатана, но пенопластовая прокладка внутри кривая!» (**ошибка `Invalid PKCS#7 Padding`**), то по этим подсказкам (Padding Oracle) можно по одному байту вычислить всё содержимое коробки.

## Почему это работает: Режим ECB, дополнение PKCS#7 и предсказуемый PRNG

Разберём три классических дефекта криптографических реализаций:

1. **Перестановка блоков в режиме `AES-ECB` (Cut-and-Paste Attack)**. В режиме `ECB` каждый 16-байтовый блок открытого текста шифруется своим ключом совершенно независимо от соседних блоков: одинаковые 16 байт входа всегда дают одинаковые 16 байт шифротекста. Если сервер формирует профиль вида `uid=10&role=user` и шифрует его в `ECB`, то блоки шифротекста можно переставлять, дублировать или склеивать из двух разных шифротекстов, зашифрованных тем же ключом.
2. **Дополнение `PKCS#7` и оракул дополнения (Padding Oracle в `AES-CBC`)**:
   - поскольку блочный шифр работает с блоками по 16 байт, неполный последний блок дополняют до 16 байт по правилу **PKCS#7**: если не хватает `N` байт (от `1` до `16`), в конец дописывают `N` байт, каждый из которых равен числу `N` (например, `0x03 0x03 0x03`, если не хватало 3 байт, или целый блок из шестнадцати байт `0x10`, если длина уже была кратна 16);
   - если сервер использует режим `CBC` **без предварительной проверки `HMAC`** (или не использует `AES-GCM`) и возвращает разные ответы на «ошибку дополнения PKCS#7» (`500 Padding Error`) и «ошибку формата данных после расшифровки» (`400 Bad JSON`), возникает **Padding Oracle**: изменяя байты предыдущего блока шифротекста `C_{i-1}` и наблюдая, когда сервер перестаёт жаловаться на дополнение (`P'_i[15] == 0x01`), можно расшифровать блок без ключа за $16 \times 256$ запросов.
3. **Небезопасный PRNG (`random` / Mersenne Twister) против криптографического CSPRNG (`os.urandom` / `secrets`)**. Обычный генератор `random.Random(seed)` создаan для моделирования и игр: если известен начальный `seed` (например, секунда времени создания токена `int(time.time())`), вся последовательность «случайных» байтов воспроизводится со 100%-ной точностью. Для ключей, солей и токенов сессий допустим только системный источник энтропии ядра (`/dev/urandom`, модуль `secrets` в Python).

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
import hashlib
import hmac


def pkcs7_pad(data, block_size=16):
    pad_len = block_size - (len(data) % block_size)
    return data + bytes([pad_len] * pad_len)


def pkcs7_unpad_constant_shape(padded, block_size=16):
    if not padded or len(padded) % block_size != 0:
        return None
    pad_len = padded[-1]
    if pad_len < 1 or pad_len > block_size:
        return None
    if padded[-pad_len:] != bytes([pad_len] * pad_len):
        return None
    return padded[:-pad_len]


def verify_then_unpad(ciphertext_blocks, tag, mac_key):
    raw = b"".join(ciphertext_blocks)
    expected_tag = hmac.new(mac_key, raw, hashlib.sha256).hexdigest()[:16]
    if not hmac.compare_digest(tag, expected_tag):
        return "rejected:invalid_mac_before_decrypt"
    plain = pkcs7_unpad_constant_shape(raw)
    if plain is None:
        return "rejected:invalid_request"
    return f"accepted:{plain.decode('ascii')}"


b1 = b"user=alex&role=u"
b2 = pkcs7_pad(b"ser")
b2_swapped = pkcs7_pad(b"admin")

mac_key = b"kairon-mac-key-2026"
valid_raw = b1 + b2
valid_tag = hmac.new(mac_key, valid_raw, hashlib.sha256).hexdigest()[:16]

print("padded_len=", len(valid_raw), "last_pad_byte=", hex(b2[-1]))
print("authentic_packet=", verify_then_unpad([b1, b2], valid_tag, mac_key))
print("swapped_block_caught=", verify_then_unpad([b1, b2_swapped], valid_tag, mac_key))
```

### Шаг 2. Запусти программу и разбери защиту от подмены блоков и Padding Oracle

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
padded_len= 32 last_pad_byte= 0xd
authentic_packet= accepted:user=alex&role=user
swapped_block_caught= rejected:invalid_mac_before_decrypt
```

Посмотри на три ключевых результата:
- функция `pkcs7_pad(b"ser")` дополнила 3-байтовый хвост до 16 байт тринадцатью байтами `0x0d` (`13` в шестнадцатеричной системе, `last_pad_byte= 0xd`), доведя общую длину сообщения `b1 + b2` до 32 байт (ровно два 16-байтовых блока);
- в `authentic_packet` функция `verify_then_unpad` сначала сверила код аутентификации `HMAC-SHA256` по схеме **Encrypt-then-MAC**, убедилась, что блоки не тронуты, и только после этого сняла дополнение `PKCS#7`, вернув `accepted:user=alex&role=user`;
- в `swapped_block_caught` второй блок попытались заменить на `b2_swapped` (`admin` с корректным дополнением `PKCS#7`). Так как проверка `HMAC` выполняется **до** разбора дополнения, подмена была мгновенно остановлена со статусом `rejected:invalid_mac_before_decrypt` — сервер даже не притронулся к проверке `PKCS#7`, поэтому никакой утечки Padding Oracle не возникает!

## Почему это работает: Почему схема Encrypt-then-MAC или шифр AEAD (`AES-GCM`, `ChaCha20-Poly1305`) закрывают оба класса атак

Когда приложение использует современный режим **AEAD** (`AES-GCM` или `ChaCha20-Poly1305`) со случайным уникальным `nonce`, каждый блок зависит от счётчика и позиции в потоке (поэтому перестановка блоков `ECB` невозможна), а тег аутентификации проверяется до выдачи любых данных (поэтому невозможен и Padding Oracle).

## Если не получилось: Частые ошибки

- **Возврат разных кодов ошибок при сбое `MAC` и сбое `PKCS#7`**: если сервер проверяет `MAC` после расшифровки (`MAC-then-Encrypt`) и сообщает клиенту отдельно `Bad Padding` и отдельно `Bad Signature`, оракул дополнения остаётся открытым. Правильный порядок — всегда проверять целостность шифротекста **до** любой попытки расшифровки и снятия дополнения, возвращая единый нейтральный ответ об ошибке.
