## Перед началом: Как реверс-инженер читает ветвления и проверки в скомпилированном коде

В модуле **Reverse Engineering** практикумов **Intro to Cybersecurity** и **Program Security** (`pwn.college`) учат восстанавливать логику программы, когда исходный код на C недоступен, а перед глазами есть только дизассемблированные инструкции (`objdump -d`, `gdb`, Ghidra или Binary Ninja).

Представь лабиринт с несколькими кодовыми дверями, ведущими в хранилище (`win` / `grant_access`). У каждой двери стоит контролёр (инструкция сравнения `cmp` или `test`), который проверяет одно конкретное условие: «Длина кода равна 8 символам?», «Первые четыре символа — `KRN-`?», «Сумма кодов остальных символов делится на 10?». Если хотя бы на одной двери ответ «нет», условный переход (`jne`, `jb`, `ja`) немедленно отправляет посетителя в общий коридор отказа (`fail_exit`).

Чтобы не подбирать пароль наугад из миллиардов вариантов, аналитик строит **граф потока управления (Control Flow Graph, CFG)**: разбивает функцию на линейные участки без ветвлений (**базовые блоки**, basic blocks), выписывает условие каждого перехода на пути к блоку успеха и математически решает полученную систему ограничений.

## Почему это работает: Базовые блоки, флаги процессора `ZF`/`CF` и инверсия условий компилятора

Разберём три опоры статического реверс-инжиниринга бинарного кода:

1. **Что такое базовый блок (Basic Block) и CFG**. Базовый блок — это последовательность инструкций с **одним входом** (первая инструкция блока) и **одним выходом** (последняя инструкция — условный или безусловный переход `jmp`/`je`/`jne` или возврат `ret`). Внутри базового блока управление всегда течёт строго сверху вниз. Соединив базовые блоки стрелками переходов (обычно зелёная стрелка для `true`, красная для `false`), дизассемблер строит граф потока управления функции (CFG).
2. **Как работают `cmp` и `test` вместе с условными переходами**:
   - инструкция `cmp regA, regB` вычисляет разность `regA - regB`, не сохраняя сам результат, но обновляя регистр флагов `RFLAGS`. Если значения равны, поднимается флаг нуля `ZF = 1` (сработает `je` / `jz` — *jump if equal*). Если не равны — `ZF = 0` (сработает `jne` / `jnz` — *jump if not equal*);
   - инструкция `test regA, regA` выполняет побитовое `AND` регистра с самим собой. Чаще всего так проверяют, равен ли регистр нулю (`test eax, eax` перед `je` / `jne`).
3. **Инверсия условий компилятором (Guard Clauses)**. В исходном коде программист часто пишет условие продолжения: `if (len == 8) { ... }`. Компилятор же почти всегда переворачивает его в проверку раннего выхода: `cmp eax, 8` → `jne block_fail`. Поэтому при чтении дизассемблера важно следить, куда ведёт ветка перехода: чтобы дойти до целевого блока `block_success`, нужно **не попасть** на ветки `jne block_fail`, то есть выполнить условие `eax == 8`.
4. **Последовательное преобразование буфера (Mangling / XOR / Shift)**. Во многих задачах `Reverse Engineering` на `pwn.college` программа сначала преобразует введённые пользователем байты в цикле (например, делает `byte ^ 0x2A` или прибавляет смещение `(byte + idx) & 0xFF`), а затем сравнивает результат с константным массивом `EXPECTED` из секции `.rodata`. Чтобы найти верный ввод, достаточно применить обратную операцию к каждому байту `EXPECTED` в обратном порядке!

## Сделай сейчас: Практика: восстанови ключ по графу проверок и обратимому преобразованию

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
EXPECTED_RODATA = [0x61, 0x79, 0x66, 0x0A, 0x21, 0x23, 0x1E, 0x19]


def check_key_cfg(candidate_bytes):
    trace = ["bb_entry"]
    if len(candidate_bytes) != 8:
        trace.append("bb_fail_len")
        return False, trace

    trace.append("bb_check_prefix")
    if candidate_bytes[:4] != b"KRN-":
        trace.append("bb_fail_prefix")
        return False, trace

    trace.append("bb_check_loop")
    for idx, b in enumerate(candidate_bytes):
        transformed = (b ^ 0x2A) + idx
        if transformed != EXPECTED_RODATA[idx]:
            trace.append(f"bb_fail_byte_{idx}")
            return False, trace

    trace.append("bb_accept")
    return True, trace


def recover_key_from_rodata(rodata):
    return bytes(((val - idx) ^ 0x2A) for idx, val in enumerate(rodata))


recovered = recover_key_from_rodata(EXPECTED_RODATA)
ok_wrong, trace_wrong = check_key_cfg(b"KRN-0000")
ok_right, trace_right = check_key_cfg(recovered)

print("recovered_key=", recovered.decode("ascii"))
print("wrong_attempt=", ok_wrong, trace_wrong)
print("right_attempt=", ok_right, trace_right)
```

### Шаг 2. Запусти программу и проследи трассу по базовым блокам

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
recovered_key= KRN-7428
wrong_attempt= False ['bb_entry', 'bb_check_prefix', 'bb_check_loop', 'bb_fail_byte_4']
right_attempt= True ['bb_entry', 'bb_check_prefix', 'bb_check_loop', 'bb_accept']
```

Разберём, как работает восстановление ключа:
- функция `check_key_cfg` моделирует типичную цепочку базовых блоков из `Reverse Engineering`: блок `bb_entry` проверяет длину (`!= 8` → `bb_fail_len`), блок `bb_check_prefix` сверяет первые 4 байта (`KRN-`), а цикл `bb_check_loop` вычисляет для каждого байта `(b ^ 0x2A) + idx` и сравнивает с таблицей `EXPECTED_RODATA`;
- пробная строка `b"KRN-0000"` прошла первые два блока, но остановилась на первом же байте после дефиса (`bb_fail_byte_4`);
- вместо перебора мы записали в `recover_key_from_rodata` строго обратную формулу: сначала вычли `idx` (`val - idx`), а затем применили `^ 0x2A` (так как операция XOR обратна сама себе). Это мгновенно дало точный ключ `KRN-7428`, который прошёл по графу до блока `bb_accept`.

## Почему это работает: Как устроено обратимое и необратимое преобразование при проверке ключа

Если программа проверяет ввод через обратимые арифметические и побитовые операции (`+`, `-`, `XOR`, побитовые циклические сдвиги `ROL`/`ROR`, перестановку байтов), то по массиву `EXPECTED_RODATA` всегда можно однозначно вычислить исходный ключ (или использовать SMT-решатель вроде `z3`). Именно поэтому настоящие системы аутентификации никогда не хранят обратимо замаскированный пароль в `.rodata`, а используют криптографически стойкие односторонние функции хеширования паролей с солью (`Argon2id`, `scrypt`, `bcrypt`).

## Если не получилось: Частые ошибки

- **Неверный порядок обратных операций**: если прямое преобразование сначала делает `XOR`, а потом прибавляет `idx` (`y = (b ^ 0x2A) + idx`), то обратное преобразование обязано выполняться **в обратном порядке** — сначала вычитание `idx`, а затем `XOR`: `b = (y - idx) ^ 0x2A`. Если сначала сделать `XOR`, а потом вычесть `idx`, ответ будет неверным, так как сложение и `XOR` не коммутируют.
