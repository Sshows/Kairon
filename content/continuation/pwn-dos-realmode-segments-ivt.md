## Перед началом: Зачем изучать 16-битный реальный режим (`pwn.college DOS Dojo`)

В официальном сообществе `pwn.college` есть необычный исторический курс — **`DOS Dojo` (`pwncollege/dos-dojo`)** с модулями `ms-dos` и `memory`. Зачем специалисту по безопасности заглядывать в эпоху 16-битного `MS-DOS` и реального режима процессора (`Real Mode`), с которого до сих пор начинает загрузку каждый процессор `x86` до переключения в защищённый 32/64-битный режим?

Потому что `Real Mode` наглядно показывает, **как выглядит компьютер вообще без аппаратной защиты памяти (`MMU`, колец привилегий `Ring 0 / Ring 3` и `NX`)**:
1. **Сегментная адресация `Segment:Offset`**: регистры в 16-битном режиме вмещают числа только до `0xFFFF` ($65\,535$ байт — 64 КБ), а адресная шина позволяла адресовать 1 мегабайт (`20 бит`, до `0xFFFFF`). Чтобы получить 20-битный физический адрес из двух 16-битных регистров (например, `CS:IP` или `DS:SI`), процессор сдвигает сегмент на 4 бита влево (умножает на `16`, то есть дописывает шестнадцатеричный ноль) и прибавляет смещение:
   $$\text{Physical Address} = (\text{Segment} \times 16) + \text{Offset} = (\text{Segment} \ll 4) + \text{Offset}$$
   Из-за этого к одной и той же ячейке физической памяти можно обратиться **тысячами разных пар** `Segment:Offset` (перекрывающиеся сегменты)!
2. **Таблица векторов прерываний `IVT (Interrupt Vector Table)` по адресу `0x00000`**: в самом начале физической оперативной памяти (первые `1024` байта, от `0x00000` до `0x003FF`) лежат 256 четырехбайтовых указателей `CS:IP` для прерываний `INT 00h` .. `INT FFh` (включая системные вызовы DOS `INT 21h`). Поскольку в реальном режиме нет таблицы страниц с правами `Read-Only` и нет разделения на `User / Kernel`, любая запущенная программа может напрямую перезаписать адрес обработчика `INT 21h` в `IVT` и перехватить все обращения к операционной системе!

## Почему это работает: Переход от `Real Mode` к `Protected / Long Mode`

Именно опыт эксплуатации полной открытости `Real Mode` привёл к созданию в архитектуре `x86` защищённого режима (`Protected Mode`) и 64-битного режима (`Long Mode`):
- таблица прерываний `IDT` переехала в защищённую память ядра (`Ring 0`), недоступную из `Ring 3`;
- страничная адресация (`Paging`) с битами `U/S` (User/Supervisor), `R/W` и `NX` изолировала виртуальное адресное пространство каждого процесса.

### Шаг 1. Создай файл `lab.py`

Создай скрипт `lab.py`:

```python
def realmode_phys_addr(segment, offset):
    if not (0 <= segment <= 0xFFFF and 0 <= offset <= 0xFFFF):
        raise ValueError("16-bit register out of range")
    return ((segment << 4) + offset) & 0xFFFFF


def ivt_entry_offset(int_num):
    # В Real Mode каждый вектор прерывания занимает 4 байта (2 байта Offset + 2 байта Segment)
    return int_num * 4


def write_interrupt_vector(int_num, new_cs, new_ip, cpu_mode="real_mode", cpl=3):
    if cpu_mode != "real_mode" and cpl > 0:
        return "fault:GPF_ring3_cannot_modify_IDT", None
    addr = ivt_entry_offset(int_num)
    return "ivt_hooked_in_real_mode", f"ivt[0x{addr:04x}]={new_cs:04x}:{new_ip:04x}"


addr_a = realmode_phys_addr(0x1000, 0x0020)
addr_b = realmode_phys_addr(0x1002, 0x0000)

print("phys_a=", hex(addr_a), "phys_b=", hex(addr_b), "same_cell=", addr_a == addr_b)
print("int21h_ivt_offset=", hex(ivt_entry_offset(0x21)))
print("dos_realmode_write=", write_interrupt_vector(0x21, 0x2000, 0x0100, cpu_mode="real_mode", cpl=3))
print("protected_ring3_write=", write_interrupt_vector(0x21, 0x2000, 0x0100, cpu_mode="long_mode", cpl=3))
```

### Шаг 2. Запусти скрипт и разбери перекрытие сегментов

Выполни в терминале:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
phys_a= 0x10020 phys_b= 0x10020 same_cell= True
int21h_ivt_offset= 0x84
dos_realmode_write= ('ivt_hooked_in_real_mode', 'ivt[0x0084]=2000:0100')
protected_ring3_write= ('fault:GPF_ring3_cannot_modify_IDT', None)
```

Разберём, что произошло:
- пара `0x1000:0x0020` (`(0x1000 << 4) + 0x0020 = 0x10020`) и пара `0x1002:0x0000` (`(0x1002 << 4) + 0x0000 = 0x10020`) указывают на **одну и ту же физическую ячейку памяти** `0x10020` (`same_cell= True`). Если наивная проверка в `Real Mode` сравнивает только числа сегментов (`segment != 0x1000`), к той же самой памяти легко обратиться через соседний сегмент `0x1002`!
- вектор системного прерывания DOS `INT 21h` (`0x21 = 33`) лежит в таблице `IVT` по смещению `33 * 4 = 132` (`0x84`);
- в `real_mode` пользовательский код беспрепятственно перезаписал вектор `ivt[0x0084]`, тогда как в `long_mode` при уровне привилегий `CPL = 3` процессор заблокировал попытку модификации таблицы прерываний исключением защиты (`fault:GPF_ring3_cannot_modify_IDT`).

### Шаг 3. Проверь заворот адреса (`20-bit wraparound`) и расчёт в Kali

В файле `lab.py` замени `0x1002, 0x0000` во втором вызове `realmode_phys_addr` на `0x1001, 0x0010`, сохрани и запусти `python3 lab.py`. Ты увидишь, что и эта третья пара даёт тот же физический адрес `0x10020`! После проверки верни исходные значения.

В терминале Kali можно одной строкой на Python перечислить сразу несколько эквивалентных пар `Segment:Offset` для любого физического адреса:

```bash
python3 -c "target = 0x10020; print([f'{seg:04x}:{target - (seg<<4):04x}' for seg in (0x1000, 0x1001, 0x1002)])"
```

## Почему это работает: Историческая линия `A20 Gate`

Что происходит в `Real Mode`, если задать максимальный сегмент `0xFFFF` и смещение `0x0020`? Сумма `(0xFFFF << 4) + 0x0020` равна `0x100010` — это 21 бит! На процессоре `8086` (с 20 линиями адреса) старший 21-й бит просто отбрасывался, и адрес сворачивался в начало памяти (`0x00010`, прямо в таблицу векторов прерываний `IVT`). Когда на `80286` появилась 21-я адресная линия (`A20`), для совместимости со старыми программами инженеры даже добавили специальный вентиль `A20 Gate`, включающий или отключающий этот заворот адреса.

## Если не получилось: Частые ошибки

- **Сложение `Segment + Offset` без сдвига сегмента на 4 бита (`<< 4`)**: в `Real Mode` сегментный регистр сдвигается ровно на 4 бита (умножается на `16`), а не на 16 бит.
