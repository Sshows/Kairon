## Перед началом: Как устроен исполняемый файл ELF и как работает точка останова в отладчике

В модулях **Introspecting** и **Debugging Refresher** курса **Computing 101** (`pwn.college`) разбирают два фундаментальных вопроса: что именно лежит внутри скомпилированного бинарного файла Linux (формат **ELF — Executable and Linkable Format**) и каким образом отладчик (`gdb`) способен остановить работающий процессор ровно на одной выбранной машинной инструкции.

Представь архитектурный проект здания. Сам файл на диске — это папка с чертежами (**секциями**, sections), где отдельно нарисованы несущие стены (машинный код `.text`), таблички с неизменяемыми надписями (строковые константы `.rodata`), шкафы с начальными запасами (инициализированные глобальные переменные `.data`) и пустые комнаты под будущие склады (неинициализированные переменные `.bss`). А когда по этому проекту возводят реальное здание в оперативной памяти, рабочие объединяют чертежи по правам доступа в крупные строительные блоки — **сегменты памяти (program headers / segments)**: один блок только для чтения и выполнения (`R-X`), другой — для чтения и записи (`RW-`).

Когда же инженер запускает программу под отладчиком `gdb` и ставит **программную точку останова (software breakpoint)** по адресу инструкции (`break *0x401156`), отладчик временно записывает по этому адресу специальный однобайтовый машинный код `0xCC` (инструкцию прерывания `int3`). Дойдя до `0xCC`, процессор приостанавливает программу и передаёт управление отладчику!

## Почему это работает: Заголовок ELF, секции `.text`/`.rodata`/`.data`/`.bss` и байт `0xCC` (`int3`)

Разберём устройство ELF-файла и работу отладчика по шагам:

1. **Магические байты заголовка ELF (`7f 45 4c 46`)**. Любой исполняемый файл и библиотека `.so` в Linux начинаются с четырёх байтов: `0x7f` и трёх букв ASCII `ELF` (`0x45`, `0x4c`, `0x46`). Пятый байт (`EI_CLASS`) указывает разрядность (`0x02` для 64-битной архитектуры `x86-64`), шестой (`EI_DATA`) — порядок байтов (`0x01` для `little-endian`), а в поле `e_entry` записан виртуальный адрес первой инструкции программы (точка входа `_start`).
2. **Главные секции ELF-файла**:
   - `.text` — исполняемые машинные инструкции функций (`main`, `verify` и др.), права доступа `r-x`;
   - `.rodata` (Read-Only Data) — строковые литералы и константы только для чтения, права `r--`;
   - `.data` — глобальные и статические переменные, которым в коде задано ненулевое начальное значение, права `rw-`;
   - `.bss` — глобальные переменные, заполняемые нулями при старте программы: на диске они почти не занимают места, а в памяти для них выделяется `rw-` область нужного размера.
3. **Как работает программный брейкпоинт (`0xCC` / `int3`) в `gdb`**:
   - когда ты вводишь `break *0x401156`, отладчик читает и сохраняет у себя оригинальный первый байт инструкции по адресу `0x401156` (например, `0x55` — инструкцию `push rbp`), а в память процесса на это место записывает байт `0xCC` (`int3`);
   - когда регистр `RIP` доходит до `0x401156` и выполняет `0xCC`, ядро посылает процессу сигнал `SIGTRAP` и будит `gdb`;
   - чтобы продолжить выполнение (`continue` или `nexti`), `gdb` возвращает оригинальный байт `0x55` обратно в память, делает один шаг процессора (`single-step`) и снова ставит `0xCC`.

## Сделай сейчас: Практика: проверь заголовок ELF, карту секций и установку точки останова `0xCC`

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
ELF_MAGIC = b"\x7fELF"


def parse_elf_header(raw_bytes):
    if raw_bytes[:4] != ELF_MAGIC:
        return {"valid": False}
    bits = 64 if raw_bytes[4] == 2 else 32
    endian = "little" if raw_bytes[5] == 1 else "big"
    entry = int.from_bytes(raw_bytes[24:32], endian)
    return {"valid": True, "bits": bits, "endian": endian, "entry": hex(entry)}


def apply_software_breakpoint(code_bytes, offset):
    memory = bytearray(code_bytes)
    saved_byte = memory[offset]
    memory[offset] = 0xCC
    return saved_byte, bytes(memory)


header = bytearray(32)
header[0:4] = b"\x7fELF"
header[4] = 2
header[5] = 1
header[24:32] = (0x401060).to_bytes(8, "little")

func_prologue = b"\x55\x48\x89\xe5\x83\xec\x10\xc3"
orig_byte, patched_code = apply_software_breakpoint(func_prologue, offset=0)

print("elf_info=", parse_elf_header(bytes(header)))
print("saved_opcode=", hex(orig_byte), "patched_hex=", patched_code.hex())
```

### Шаг 2. Запусти программу и изучи вывод

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
elf_info= {'valid': True, 'bits': 64, 'endian': 'little', 'entry': '0x401060'}
saved_opcode= 0x55 patched_hex= cc4889e583ec10c3
```

Посмотри на обе строки вывода:
- `parse_elf_header` проверил сигнатуру `\x7fELF`, определил 64-битный формат (`raw_bytes[4] == 2`), порядок байтов `little-endian` (`raw_bytes[5] == 1`) и прочитал 8-байтовый адрес точки входа `0x401060`;
- в прологе функции `func_prologue` (`55 48 89 e5...`, то есть `push rbp; mov rbp, rsp...`) функция `apply_software_breakpoint` сохранила оригинальный первый байт `0x55` (`saved_opcode= 0x55`) и заменила его в памяти на `0xCC` (`cc4889e583ec10c3`), чтобы процессор остановился сразу при входе в функцию.

### Шаг 3. Поставь точку останова на выход из функции и проверь ELF в Kali

В файле `lab.py` измени `offset=0` на `offset=7` (последний байт `0xc3` в `func_prologue` — это инструкция возврата `ret`), сохрани и запусти `python3 lab.py`. Теперь `saved_opcode=` станет `0xc3`, а `patched_hex=` станет `554889e583ec10cc` — точка останова стоит прямо перед возвратом из функции! После проверки верни `offset=0`.

В терминале Kali ты можешь посмотреть настоящий заголовок и секции системной утилиты `/bin/ls` стандартной командой `readelf`:

```bash
readelf -h -S /bin/ls | head -n 35
```

В строке `Magic:` ты увидишь те самые байты `7f 45 4c 46 02 01`, в `Entry point address:` — адрес старта программы, а ниже — таблицу секций (`.interp`, `.text`, `.rodata`, `.data`, `.bss`).

## Почему это работает: Как защитный анализ отличает честную отладку от самомодифицирующегося кода

Так как программная точка останова временно меняет байт в памяти `.text` на `0xCC`, некоторые программы проверяют контрольную сумму своего кода в памяти, чтобы обнаружить отладчик (приём *anti-debugging* с поиском байта `0xCC`). В таких случаях при анализе в `gdb` используют **аппаратные точки останова (hardware breakpoints, команда `hbreak`)**, которые хранят адрес остановки прямо в отладочных регистрах процессора (`DR0–DR3`), вообще не изменяя байты в секции `.text`!

## Если не получилось: Частые ошибки

- **Путаница между смещением в файле на диске (File Offset) и виртуальным адресом в памяти (Virtual Address)**: в ELF-файле с отключённым PIE секция `.text` может лежать в файле со смещения `0x1000`, но загружаться в виртуальную память по адресу `0x401000`. В `readelf -S` оба числа показаны рядом в колонках `Address` и `Off`.
- **Попытка поставить `break` по имени функции в «очищенном» (`stripped`) бинарнике**: если из ELF-файла удалена таблица символов `.symtab` (командой `strip`), имя `main` исчезает, и точку останова в `gdb` ставят по явному адресу со звёздочкой: `break *0x401156`.
