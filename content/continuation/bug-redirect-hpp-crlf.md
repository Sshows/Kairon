## Перед началом: Один запрос проходит через несколько читателей

Посетитель нажал кнопку, браузер отправил запрос, его прочитал прокси, затем сервер и библиотека приложения. Каждому слою нужно понять, где адрес, где название поля, где его значение. Если два слоя понимают одну строку по-разному, проверка на первом слое может не соответствовать действию последнего.

Представь бланк доставки с двумя строками «получатель». Сотрудник при приёме проверил первую, а курьер прочитал последнюю. Проблема не в количестве чернил, а в неоднозначном правиле. Похожий вопрос задаёт исследователь: «Какое именно значение проверили и какое использовали?» Аналогия помогает понять расхождение, но протоколы строже бумаги: важны точные байты, декодирование и конкретный парсер.

Сегодня три разные ошибки. Они связаны обработкой запроса, но требуют разных доказательств и исправлений. Не называй любую странную строку «инъекцией» без указания места, где она получает специальный смысл.

## Почему это работает: Open Redirect: кто выбирает адрес следующего перехода

После входа сайт может вернуть пользователя к открытой ранее странице. Если сервер без ограничения принимает `next` как произвольный внешний URL, его адрес становится отправной точкой для перехода на другой сайт. Это называют **открытым перенаправлением**. Внешняя страница может выглядеть как продолжение знакомого сайта, хотя прежний сервер уже не управляет её содержимым.

Наличие кнопки со ссылкой само по себе не доказывает уязвимость. Нужно установить, какое значение управляет переходом, куда ведёт фактический ответ и нарушает ли это правила приложения. Для внутреннего «вернуться после входа» часто проще принимать короткий код назначения, например `profile`, и выбирать реальный путь из серверной таблицы. Скрытая проверка только в JavaScript не ограничивает запрос, отправленный другим способом.

## Почему это работает: HPP: повторяющийся параметр

**HTTP Parameter Pollution** связан с неоднозначной обработкой параметров. Запрос `role=user&role=admin` содержит два значения одного имени. Одни библиотеки дают список, другие первое или последнее значение. Повтор может быть нормальным для фильтра с несколькими категориями. Для одиночного поля требуется явное правило. А роль вошедшего пользователя вообще нельзя назначать по такому параметру: она должна происходить из проверенной серверной записи.

## Почему это работает: CRLF: перенос строки становится разделителем

CR — байт 13 (`\r`), LF — байт 10 (`\n`). В некоторых представлениях HTTP они разделяют строки заголовков. Если значение, которое должно быть обычным текстом, позволяет создать новую строку заголовка, граница данных нарушается. В URL такие байты могут быть записаны как `%0D` и `%0A`. Важно, на каком шаге произошло декодирование: строка из шести печатных символов и два управляющих байта — разные входы.

Современный серверный API обычно запрещает недопустимые значения заголовков. Используй его, а не собирай ответ конкатенацией строк. Наш следующий опыт лишь проверит правило для текстового поля; он не создаёт настоящий HTTP-ответ и не доказывает поведение конкретного прокси.

## Сделай сейчас: Практика: наблюдай каждое правило отдельно

Вставь код в `lab.py`:

```python
from urllib.parse import parse_qs, unquote

values = parse_qs("role=user&role=admin")["role"]
print("first=", values[0], "last=", values[-1])
print("single_value=", len(values) == 1)

destinations = {"home": "/", "profile": "/profile"}
for requested in ["profile", "https://example.test/other"]:
    print("redirect=", requested, "result=", destinations.get(requested, "rejected"))

def checked_text(raw):
    decoded = unquote(raw)
    if "\r" in decoded or "\n" in decoded:
        return "rejected"
    return "accepted"

for raw in ["receipt-17", "receipt%0D%0AX-Demo:yes"]:
    print("text=", repr(raw), "result=", checked_text(raw))
```

Запусти `python3 lab.py` в терминале. В первой строке увидишь `first= user last= admin`, затем `single_value= False`. Это не запрос к настоящему серверу: мы показали две возможные политики чтения одного разобранного списка. Для программы они различаются, поэтому нельзя молча считать их взаимозаменяемыми.

Далее код назначения `profile` даёт `/profile`, а строка с внешним адресом — `rejected`. Интернет не используется, браузер никуда не переходит. `.get` ищет точное имя в таблице. Не нужно заменять `example.test` реальным доменом: это намеренно вымышленный текст для проверки отказа.

Последние две строки сравнят обычную квитанцию и значение с закодированным переносом. `unquote` в нашей модели выполняет одно декодирование URL, `repr` выводит удобное для чтения представление исходной строки. После декодирования функция ищет **оба** управляющих символа. Для первого значения ожидается `accepted`, для второго `rejected`. Это не универсальная очистка всех HTTP-вводов: реальное приложение должно знать, какие слои и сколько раз декодируют значение, и использовать штатный API заголовков.

## Сделай сейчас: Убедись, что понимаешь результат

Убери второй `role` и повтори опыт: `first` и `last` совпадут, `single_value` станет True. Потом верни его. Добавь новый разрешённый код назначения в `destinations`, например `help: /help` с правильными кавычками в Python, и проверь его отдельным элементом списка. Разрешение появится потому, что его задал разработчик, а не потому, что строка «выглядит похожей» на свой домен.

Не пытайся заменить таблицу проверкой `startswith("https://trusted")`: префикс не равен проверке точного имени узла, схемы и допустимого маршрута. Разрешённый переход тоже может вести к странице, которая затем перенаправляет ещё раз; цепочку рассматривают целиком в отдельной проверке.

Если появилась ошибка `KeyError: role`, ты удалил параметр целиком, а программа по-прежнему обращается к нему как к обязательному. Это хороший повод задать политику отсутствующего поля отдельно. `SyntaxError` обычно означает потерянную кавычку либо запятую. Не решай такие ошибки запуском от root: привилегии не исправляют синтаксис.

Для отчёта выбери **один** проверяемый механизм: вход, слой разбора, использованное значение, ожидаемое ограничение, наблюдаемый результат. Например: «Для одиночного поля модель получила два значения и отказала до использования. Проверка выполнена на синтетической строке; сетевой стек не проверялся». Для реального бага дополнительно нужны доказанное действие и влияние в разрешённой среде. Совпадение строки с названием известной техники недостаточно.
