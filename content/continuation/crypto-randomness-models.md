## Сначала реши, от кого и что защищаешь

Представь ссылку для сброса пароля. Кто её знает, тот в пределах срока может подтвердить действие. Если значение ссылки легко предсказать, хорошее шифрование остальной базы не исправит эту проблему. Начинать нужно с **модели угроз**: что защищаем, что умеет наблюдать и менять другой участник, какую гарантию хотим получить.

Для учебного токена цель такова: посторонний, даже увидев прежние токены и зная способ генерации, не должен практически угадывать новый. При этом он может отправлять запросы в пределах ограничений сервиса. Мы не предполагаем, что наш компьютер уже полностью захвачен: в такой ситуации чтение памяти и ключей требует другого уровня защиты.

Модель угроз — не длинный список страшных слов. Это договор об условиях задачи. Например, запертая дверь защищает от человека без ключа, но не от того, кому ты добровольно выдал дубликат. В цифровой системе нужно столь же явно назвать, какие секреты доступны участникам и какие действия приложение принимает по одному владению токеном.

## Случайно выглядит — не значит непредсказуемо

Обычный генератор псевдослучайных чисел получает исходное состояние и по алгоритму выдаёт последовательность. Для игры или моделирования это удобно: одинаковый **seed**, то есть начальное зерно, позволяет воспроизвести опыт. Но воспроизводимость не должна превращаться в возможность угадать секрет. Длинная строка из предсказуемого генератора остаётся предсказуемой.

**CSPRNG** — генератор с криптографическими требованиями к непредсказуемости. При корректном устройстве знание части выходных значений не даёт практичного способа вычислить остальные. В Python для обычных секретов есть модуль `secrets`, который использует подходящий источник операционной системы. Не нужно собирать свой источник из времени, номера процесса и движений мыши.

**Энтропия** в этом контексте помогает описать неопределённость выбора. Если равновероятно выбирается одно из 16 значений, требуется 4 бита, чтобы различить все варианты. Но длина записи не равна энтропии: строка из ста повторённых нулей длинная, а выбора в ней нет. И статистически разнообразный файл не обязательно непредсказуем: известный алгоритм может выдавать красивую последовательность заранее.

## Практика: воспроизведение и криптографический источник

Сохрани в `lab.py`:

```python
import random
import secrets

first = random.Random(17)
second = random.Random(17)
a = [first.getrandbits(32) for _ in range(4)]
b = [second.getrandbits(32) for _ in range(4)]
print("same_seed_same_values=", a == b)
print("demo_sequence=", a)

token = secrets.token_hex(16)
print("demo_token=", token)
print("hex_characters=", len(token))
print("random_bytes=", len(bytes.fromhex(token)))
```

Запусти `python3 lab.py`. Первая строка должна показать True. Точные числа в `demo_sequence` для понимания не нужны: важно, что два отдельных генератора с одним seed дали одинаковую последовательность. `range(4)` повторяет действие четыре раза, `getrandbits(32)` выдаёт 32-битное значение. Число 17 здесь фиксировано для **воспроизводимого моделирования**, это не рекомендуемая настройка безопасности.

Вторая часть создаст учебный токен из 16 случайных байтов. `token_hex` представляет каждый байт двумя шестнадцатеричными знаками, поэтому `hex_characters` будет 32, а `random_bytes` — 16. Следующий запуск обычно даст другой токен. Отличие двух строк само по себе не является доказательством качества генератора: для выбора источника опираются на его назначение и устройство, а не на внешний вид одного результата.

В этом опыте токен нигде не используется и ничего не открывает. В настоящем сервисе токены не следует печатать в общедоступный журнал или отправлять в отчёт. Секрет, попавший в чужие руки, нельзя «сделать безопаснее» красивым названием алгоритма. Его отзывают и выпускают заново по правилам приложения.

## Соль, nonce и секретный ключ — разные требования

**Ключ** должен оставаться секретным и иметь достаточную стойкость. **Соль** в схеме хранения пароля обычно открыта: она делает одинаковые пароли разными входами функции и мешает повторно использовать заранее посчитанную таблицу сразу для всех пользователей. Это не заменяет медленную специализированную функцию хранения паролей и не усиливает короткий пароль до стойкости случайного ключа.

**Nonce** — значение с требованиями конкретной схемы. В AES-GCM повтор nonce под одним ключом опасен, хотя сам nonce не секрет. Для других режимов важна ещё и непредсказуемость IV. Поэтому совет «везде достаточно случайной строки» слишком расплывчат. Нужно прочитать требования режима и организовать жизненный цикл значений, включая перезапуск процесса и несколько серверов.

Бытовой пример: номер посылки можно показывать, но нельзя бездумно выдавать один и тот же номер двум отправлениям. Пароль от склада показывать нельзя. Оба являются строками в программе, однако требования к ним различаются. Аналогия не определяет криптографические параметры — их задаёт выбранная схема.

## Почему стойкий токен всё равно требует правил сервиса

Случайный токен не решает все задачи регистрации. Нужны срок, привязка к нужной операции и аккаунту, одноразовое использование, ограничение числа попыток и безопасное хранение. Для короткого кода из шести цифр всего миллион вариантов: даже при равномерной генерации онлайн-подбор надо ограничивать. Такой код не обладает пространством вариантов 128-битного случайного значения.

Если хранить токен для проверки, часто сохраняют подходящий проверочный отпечаток, а не сам действующий секрет, и сравнивают по правилам используемой библиотеки. Коды с небольшим пространством требуют дополнительных мер против перебора утёкшей базы; одного быстрого хеша без секрета недостаточно. Конкретное решение выбирают с учётом модели угроз, а не по слову «SHA» в названии.

## Ошибки и самостоятельный вывод

Если случайные строки отличаются от примера — это ожидаемо. Если два `Random(17)` перестали давать одинаковые списки, проверь, не сделал ли лишний вызов только у одного генератора: состояние меняется после каждого получения значения. Если назвал свой файл `random.py` или `secrets.py`, Python может импортировать его вместо библиотеки; верни имя `lab.py` и убери конфликтующий учебный файл из этой папки.

В заметке ответь на три вопроса: какой участник пытается угадать значение, какие прежние сведения ему доступны и что ограничивает число попыток? Затем объясни, почему для воспроизводимого теста удобен фиксированный seed, а для действующего токена — криптографический источник. Это и есть связь между механизмом и задачей, а не просто запомненная команда.
