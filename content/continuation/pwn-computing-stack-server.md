## Перед началом: Как функция помнит, куда вернуться, и как веб-сервер читает байты из сети

Во второй части курса **Computing 101** на `pwn.college` (модули `Advanced Memory`, `Debugging Refresher` и финальный проект `Building a Web Server`, лицензия BSD-2-Clause) две темы соединяются в одну картину: как функции используют **стек вызовов (call stack)** для хранения локальных данных и как программа шаг за шагом превращает байты из сетевого сокета в осмысленный HTTP-запрос.

Представь стопку рабочих папок на столе инженера. Когда инженер начинает подзадачу, он кладёт сверху новый чистый лист (**кадр стека**, *stack frame*), записывает вверху листа номер страницы, к которой нужно вернуться после завершения (**адрес возврата**, *return address*), а ниже ведёт черновые расчёты (локальные переменные). Закончил подзадачу — снял верхний лист со стопки и продолжил работу ровно с записанной страницы.

А когда этот же процесс работает как **веб-сервер**, он открывает сетевую дверь через цепочку системных вызовов `socket` → `bind` → `listen` → `accept` → `recv`, получает в буфер на стеке обычные текстовые строки HTTP-запроса (`GET /index.html HTTP/1.1\r\nHost: localhost\r\n\r\n`) и разбирает их по разделителям.

## Почему это работает: Указатели стека RSP/RBP и структура сырого HTTP-запроса

Разберём оба механизма без магии:

1. **Кадр стека (Stack Frame) в x86-64**. В процессоре x86-64 стек в памяти растёт **сверху вниз** (от старших адресов к младшим). Два регистра следят за текущим кадром:
   - **`rbp` (Base Pointer)** — указывает на опорную точку текущего кадра функции;
   - **`rsp` (Stack Pointer)** — указывает на текущую вершину стека (самый младший занятый адрес).
   При вызове функции (`call`) процессор уменьшает `rsp` на 8 байт и записывает туда **адрес возврата** (адрес следующей инструкции после `call`). Внутри функции локальные переменные размещаются ниже `rbp` (например, по адресам `rbp - 8`, `rbp - 16`). При выходе (`ret`) процессор забирает адрес возврата с вершины стека и переходит по нему.
2. **Разбор HTTP-запроса из сокета**. На уровне системного вызова `recv` (или `read` из клиентского сокета) сервер получает не готовый словарь, а непрерывный поток байтов. В HTTP/1.1:
   - первая строка (**стартовая строка**) содержит метод, путь и версию протокола через пробел: `GET /status HTTP/1.1`;
   - далее идут строки заголовков `Имя: Значение`, разделённые парой символов возврата каретки и перевода строки `\r\n` (`CRLF`, байты `0x0d 0x0a`);
   - пустая строка `\r\n\r\n` (два перевода подряд) отмечает **точную границу между заголовками и телом запроса**. Всё, что идёт после `\r\n\r\n`, является телом (`body`), длину которого для `POST`-запросов сверяют с заголовком `Content-Length`.

### Шаг 1. Сохрани код в файл `lab.py`

```python
class StackModel:
    def __init__(self, top_address=0x7FFF1000):
        self.rsp = top_address
        self.frames = []

    def call_function(self, name, return_rip, local_bytes):
        aligned = (local_bytes + 15) // 16 * 16
        self.rsp -= 8 + aligned
        frame = {"name": name, "return_rip": hex(return_rip), "rsp": hex(self.rsp), "locals": aligned}
        self.frames.append(frame)
        return frame

    def ret_function(self):
        frame = self.frames.pop()
        self.rsp += 8 + frame["locals"]
        return frame["return_rip"]


stack = StackModel()
f1 = stack.call_function("handle_client", 0x401120, 24)
f2 = stack.call_function("parse_http", 0x401280, 32)
print("active_depth=", len(stack.frames), "top_rsp=", f2["rsp"])
print("returned_to=", stack.ret_function(), "restored_rsp=", hex(stack.rsp))


def parse_raw_http(raw_bytes):
    header_blob, sep, body = raw_bytes.partition(b"\r\n\r\n")
    if not sep:
        return None
    lines = header_blob.decode("iso-8859-1").split("\r\n")
    method, path, version = lines[0].split(" ", 2)
    headers = {}
    for line in lines[1:]:
        key, _, value = line.partition(":")
        headers[key.strip().lower()] = value.strip()
    length = int(headers.get("content-length", "0"))
    return {"method": method, "path": path, "version": version, "host": headers.get("host"), "body": body[:length].decode("utf-8")}


packet = b"POST /submit HTTP/1.1\r\nHost: 127.0.0.1:8080\r\nContent-Length: 11\r\n\r\nflag=ok-101EXTRA"
parsed = parse_raw_http(packet)
print("http_route=", parsed["method"], parsed["path"], "body=", parsed["body"])
```

## Почему это работает: Как минимальный сервер в Computing 101 связан с безопасностью

В финальном модуле `Building a Web Server` курса **Computing 101** на `pwn.college` студент пишет HTTP-сервер на ассемблере x86-64: вызывает `socket(AF_INET, SOCK_STREAM, 0)`, привязывает адрес `bind`, включает ожидание `listen`, принимает соединение `accept`, читает запрос `read`, открывает запрошенный файл `open` и отправляет ответ `write`.

Когда видишь сервер на таком низком уровне, сразу становятся понятны три фундаментальных правила безопасности:
- если при чтении из сокета (`read`) указать размер больше, чем размер буфера, выделенного в кадре стека, лишние байты перезапишут соседние переменные и сохранённый адрес возврата `return_rip`;
- если путь из первой строки HTTP-запроса (`GET /...`) передать в системный вызов `open` без нормализации и проверки базовой папки, клиент сможет запросить файлы за пределами каталога сайта;
- если не проверять границу `\r\n\r\n` и `Content-Length`, сервер может прочитать неполный запрос или смешать два соседних запроса в одном соединении.

## Если не получилось: Частые ошибки

- **Функция `parse_raw_http` вернула `None`**: это происходит, если в строке запроса вместо парных символов `\r\n\r\n` оказались одиночные `\n\n`. В протоколе HTTP разделителем строк по стандарту является именно `\r\n`.
- **Не сходится адрес `rsp` при ручном счёте**: помни, что адреса выводятся в шестнадцатеричной системе (`0x1000 - 0x28 = 0x0fd8`, а `0x0fd8 - 0x28 = 0x0fb0` или `0x0fc0` в зависимости от размера кадра).
