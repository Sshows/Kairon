## Перед началом: Как ошибки индексации превращаются в чтение/запись по произвольному адресу и как `Safe-Linking` защищает список `tcache`

В модулях **Exploitation Primitives (Memory Mastery)** и **Dynamic Allocator Exploitation** курса **Software Exploitation** (`pwn.college`) разбирают два ключевых механизма анализа безопасности памяти:
1. как обычная ошибка проверки индекса массива (`array[idx]`) превращается в примитив **произвольного чтения (Arbitrary Address Read, AAR)** или **произвольной записи (Arbitrary Address Write, AAW)**;
2. как современные версии стандартной библиотеки `glibc` (начиная с `glibc 2.32`) защищают односвязный список свободных блоков кучи `tcache` и `fastbins` от подмены указателя `next` с помощью маскирования **Safe-Linking**.

Представь камеру хранения с пронумерованными ячейками от `0` до `7`, где каждая ячейка занимает ровно 8 байт. Если система выдачи вычисляет адрес ячейки по формуле `базовый_адрес + индекс * 8`, но забывает проверить, что `0 <= индекс < 8`, то при запросе ячейки с индексом `-4` или `250` аппарат обратится к памяти далеко за пределами шкафа! А чтобы злоумышленник не мог незаметно переписать указатель `next` в свободном списке кучи `tcache`, аллокатор `glibc` перемешивает каждый указатель `next` со случайным адресом самой страницы кучи (ASLR) и проверяет, что адрес блока кратен 16 байтам.

## Почему это работает: Индексация со знаком, AAR/AAW и формула `Safe-Linking`

Разберём оба механизма на уровне адресов и битовых операций:

1. **От выхода за границы массива (Out-of-Bounds, OOB) к AAR/AAW**. Пусть массив 8-байтовых элементов `uint64_t slots[8]` начинается по базовому адресу `base_addr`. Обращение `slots[i]` обращается к адресу `target = base_addr + i * 8`:
   - если переменная индекса `i` объявлена со знаком (`int i`) и проверяется только сверху (`if (i < 8)`), то отрицательный индекс `i = -2` проходит проверку и читает память **перед** массивом (`base_addr - 16`);
   - если же индекс вообще не ограничен, то подобрав `i = (target_addr - base_addr) // 8`, программа получает чтение или запись по любому выровненному адресу относительно `base_addr`.
2. **Уязвимость отравления списка `tcache` (tcache poisoning) в старых версиях `glibc`**. В `glibc 2.27–2.31` свободный блок в корзине `tcache` хранил в своих первых 8 байтах открытый указатель `fd` (`next`) на следующий свободный блок. Если из-за ошибки `Use-After-Free` программа перезаписывала эти 8 байт произвольным адресом `X`, то второй последующий вызов `malloc` возвращал указатель прямо на адрес `X`.
3. **Защита `Safe-Linking` в `glibc 2.32+`**. Чтобы защитить указатель `next` внутри свободного чанка, `glibc` применяет два правила:
   - **Маскирование указателя (Pointer Mangling)**: вместо открытого значения `next` в чанк по адресу `chunk_addr` записывается замаскированное число `mangled = next ^ (chunk_addr >> 12)`. Сдвиг `chunk_addr >> 12` берёт номер виртуальной страницы кучи, который случаен благодаря **ASLR**. Без знания базового адреса кучи вычислить корректное значение `mangled` невозможно!
   - **Проверка выравнивания на 16 байт**: в 64-битной `glibc` любой валидный чанк кучи обязан начинаться по адресу, кратному `16` (`addr & 0xF == 0`). При извлечении блока из `tcache` аллокатор расшифровывает указатель и сразу проверяет `if (unmangled & 0xF != 0) -> malloc(): unaligned tcache chunk detected`.

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
def safe_link_encode(chunk_addr, next_ptr):
    return next_ptr ^ (chunk_addr >> 12)


def safe_link_pop(chunk_addr, mangled_ptr):
    unmangled = mangled_ptr ^ (chunk_addr >> 12)
    if unmangled % 16 != 0:
        return "aborted:unaligned_tcache_chunk", hex(unmangled)
    return "allocated:ok", hex(unmangled)


def read_slot(slots, index, strict_bounds=True):
    if strict_bounds and not (0 <= index < len(slots)):
        return "rejected:index_out_of_bounds"
    if not strict_bounds and index < len(slots):
        return f"read_value:{slots[index]}"
    return "rejected:index_out_of_bounds"


chunk_at = 0x555555756290
valid_next = 0x555555756200
encoded = safe_link_encode(chunk_at, valid_next)

print("mangled_ptr=", hex(encoded))
print("valid_pop=", safe_link_pop(chunk_at, encoded))
print("corrupted_raw_Overwrite=", safe_link_pop(chunk_at, 0x404088))
print("signed_bug_vs_strict=", read_slot(["s0", "s1", "SECRET_BEFORE"], -1, strict_bounds=False), read_slot(["s0", "s1", "SECRET_BEFORE"], -1, strict_bounds=True))
```

**Ожидаемый результат на экране:**

Разберём вывод по шагам:
- `safe_link_encode` замаскировал указатель `0x555555756200` с помощью `chunk_at >> 12` (`0x555555756`), получив в памяти `0x555000203556`;
- при штатном извлечении (`valid_pop`) повторный `XOR` с `chunk_at >> 12` вернул исходный адрес `0x555555756200`, который кратен 16 (`0x...200 % 16 == 0`), поэтому выделение прошло штатно (`allocated:ok`);
- когда в чанк без учёта `Safe-Linking` напрямую записали адрес `0x404088` (`corrupted_raw_Overwrite`), при расшифровке получилось невыровненное число `0x5551517de` (оканчивается на `e`, не кратно 16), и аллокатор мгновенно остановил программу (`aborted:unaligned_tcache_chunk`);
- в `signed_bug_vs_strict` проверка только верхней границы (`index < len(slots)`) пропустила отрицательный индекс `-1`, тогда как двусторонняя проверка `0 <= index < len(slots)` заблокировала его (`rejected:index_out_of_bounds`).

## Почему это работает: Как правильно писать проверку индекса в C, Rust и Python

В языках C и C++ для индексов и размеров всегда используют беззнаковый тип `size_t` или проверяют обе границы `index >= 0 && index < count`. При использовании `size_t` любое отрицательное число при приведении типов превращается в огромное положительное число (например, `-1` становится `0xFFFFFFFFFFFFFFFF`), поэтому одна проверка `idx < count` сразу отсекает и выход за верхнюю границу, и отрицательные значения!

## Если не получилось: Частые ошибки

- **Почему в `Safe-Linking` сдвиг равен именно 12 битам (`>> 12`)**: размер стандартной страницы виртуальной памяти в `x86-64` равен $4096 = 2^{12}$ байт. Младшие 12 бит адреса — это смещение внутри страницы (оно не меняется при рандомизации ASLR), а биты начиная с 12-го и старше содержат случайную базу страницы, выбранную ядром при запуске процесса.
