## Перед началом: Чем переменные оболочки отличаются от переменных окружения процесса

В модулях **Variables**, **Processes** и **Shenanigans** практикума **Linux Luminarium** (`pwn.college`) подробно разбирают невидимый контекст, который передаётся каждой запускаемой программе по наследству от родительского процесса: **массив переменных окружения (`envp` / environment variables)**, область видимости подоболочек (subshells) и механизм динамического загрузчика `ld.so`.

Представь командировку сотрудника из главного офиса в филиал. Заметки, которые сотрудник написал карандашом на своём настольном черновике (**локальные переменные оболочки**), остаются лежать на столе в главном офисе — в филиале о них никто не знает. А вот документы, вложенные в официальную дорожную папку (**экспортированные переменные окружения**, помеченные командой `export`), автоматически копируются и вручаются каждому дочернему процессу, который этот сотрудник запускает!

Через переменные окружения программы узнают путь к домашнему каталогу (`HOME`), язык сообщений (`LANG`), список каталогов поиска программ (`PATH`), а динамический загрузчик Linux проверяет специальные переменные вроде `LD_PRELOAD` и `LD_LIBRARY_PATH`. Понимание того, какие переменные наследуются дочерними процессами, а какие сбрасываются при переходе через привилегированную границу `setuid`, критически важно при аудите безопасности Linux.

## Почему это работает: Локальные переменные, `export`, подоболочки и `LD_PRELOAD`

Разберём четыре правила работы окружения в Linux:

1. **Локальная переменная против экспортированной (`export`)**. Если в терминале написать `SECRET_KEY="kairon_local"`, переменная существует только внутри текущей оболочки `bash`. Запущенный следом скрипт `python3 lab.py` является дочерним процессом и **не увидит** `SECRET_KEY` в своём словаре `os.environ`. Чтобы переменная попала в таблицу окружения дочерних процессов, её нужно пометить на экспорт: `export SECRET_KEY="kairon_env"` — либо передать одноразово только для одной команды: `SECRET_KEY="once" python3 lab.py`.
2. **Изоляция подоболочки `( ... )` и `$( ... )`**. Когда команды выполняются внутри круглых скобок `( cd /tmp && EXPORTED="sub" )` или в подстановке вывода `$(...)`, оболочка создаёт отдельный дочерний процесс (subshell). Он получает копию родительских переменных, но любые изменения переменных и каталога `cd` внутри подоболочки **никогда не меняют** состояние родительской оболочки после завершения скобок.
3. **Динамический загрузчик и `LD_PRELOAD`**. Перед тем как передать управление функции `main()` обычной программы, динамический загрузчик Linux (`ld-linux.so`) читает переменную `LD_PRELOAD`. Если в ней указан путь к разделяемой библиотеке `.so`, загрузчик загружает её **раньше** стандартной библиотеки `libc.so.6`. Это позволяет переопределить стандартные функции (например, `puts`, `time`, `strcmp`) для отладки или тестирования без перекомпиляции самой программы.
4. **Защита `AT_SECURE` для привилегированных программ (`setuid`)**. Что было бы, если бы обычный пользователь мог задать `LD_PRELOAD=./my_hook.so` и запустить программу с битом `setuid root` (например, `/usr/bin/sudo` или `/usr/bin/passwd`)? Тогда код пользователя выполнился бы с правами `root`! Чтобы этого не произошло, при запуске любого бинарного файла, у которого `euid != uid` (сработал бит `setuid`), ядро Linux включает флаг `AT_SECURE`, и динамический загрузчик принудительно **игнорирует и очищает** опасные переменные (`LD_PRELOAD`, `LD_LIBRARY_PATH`), если библиотека не лежит в доверенном системном каталоге с битом `setuid`.

## Сделай сейчас: Практика: проверь наследование окружения, подоболочку и фильтр `AT_SECURE`

### Шаг 1. Сохрани код в файл `lab.py`

Вставь следующий код в открытый редактор Mousepad, нажми **Ctrl+S** и закрой редактор:

```python
DANGEROUS_LD_VARS = {"LD_PRELOAD", "LD_LIBRARY_PATH", "LD_AUDIT"}


def spawn_child_env(shell_vars, exported_keys, inline_overrides=None, is_setuid=False):
    child_env = {k: v for k, v in shell_vars.items() if k in exported_keys}
    if inline_overrides:
        child_env.update(inline_overrides)
    if is_setuid:
        for var in DANGEROUS_LD_VARS:
            child_env.pop(var, None)
    return child_env


shell_state = {
    "PATH": "/usr/bin:/bin",
    "LOCAL_NOTE": "draft_only",
    "API_MODE": "staging",
    "LD_PRELOAD": "/tmp/custom_trace.so",
}
exported = {"PATH", "API_MODE", "LD_PRELOAD"}

normal_child = spawn_child_env(shell_state, exported, inline_overrides={"REQ_ID": "42"})
setuid_child = spawn_child_env(shell_state, exported, is_setuid=True)

print("normal_child_keys=", sorted(normal_child.keys()))
print("local_note_leaked=", "LOCAL_NOTE" in normal_child)
print("setuid_child_keys=", sorted(setuid_child.keys()))
```

### Шаг 2. Запусти программу и сравни словари окружения

В терминале выполни:

```bash
python3 lab.py
```

**Ожидаемый результат на экране:**

```text
normal_child_keys= ['API_MODE', 'LD_PRELOAD', 'PATH', 'REQ_ID']
local_note_leaked= False
setuid_child_keys= ['API_MODE', 'PATH']
```

Разберём, что показала модель:
- переменная `LOCAL_NOTE` была задана в оболочке, но не добавлена в множество `exported`, поэтому в дочерний процесс она не попала (`local_note_leaked= False`);
- при запуске обычного непривилегированного процесса (`normal_child`) в его окружение перешли все экспортированные переменные (`API_MODE`, `LD_PRELOAD`, `PATH`) плюс одноразовое переопределение `REQ_ID=42`;
- при запуске привилегированного `setuid`-процесса (`setuid_child`, `is_setuid=True`) фильтр загрузчика `AT_SECURE` автоматически удалил `LD_PRELOAD`, оставив только безопасные переменные `['API_MODE', 'PATH']`.

### Шаг 3. Проверь передачу переменной для одной команды в Kali

В файле `lab.py` добавь `"LOCAL_NOTE"` в множество `exported = {"PATH", "API_MODE", "LD_PRELOAD", "LOCAL_NOTE"}`, сохрани и запусти `python3 lab.py`. Теперь `local_note_leaked=` станет `True`, а `LOCAL_NOTE` появится в обоих дочерних процессах. После проверки верни исходную строку `exported = {"PATH", "API_MODE", "LD_PRELOAD"}`.

В терминале Kali проверь разницу между локальной переменной и одноразовым окружением команды с помощью утилиты `env`:

```bash
ONLY_SHELL="hidden_value"
env | grep ONLY_SHELL || echo "Не видна в дочернем процессе env"
ONLY_SHELL="passed_once" env | grep ONLY_SHELL
```

В первом вызове `env` переменная `ONLY_SHELL` отсутствует (срабатывает ветка `Не видна в дочернем процессе env`), а во втором вызове префикс `ONLY_SHELL="passed_once"` передаёт её прямо в окружение процесса `env`.

## Почему это работает: Почему секреты в переменных окружения требуют осторожности

Переменные окружения удобны для настройки контейнеров и сервисов (`.env`), но у них есть важное свойство: они автоматически наследуются **всеми** дочерними процессами, которые запускает приложение, и в Linux их можно прочитать через файл `/proc/<PID>/environ` (если у проверяющего тот же `UID`). Поэтому в защищённых приложениях перед вызовом внешних утилит словарь окружения явно очищают, оставляя только минимальный список безопасных ключей (`PATH`, `LANG`).

## Если не получилось: Частые ошибки

- **Пробел после имени переменной в конструкции `VAR=value cmd`**: если написать `API_MODE = staging`, оболочка воспримет `API_MODE` как имя программы, а `=` и `staging` — как её аргументы. В присваивании переменных в `bash`/`zsh` пробелов вокруг знака `=` быть не должно: `API_MODE="staging"`.
- **Ожидание, что скрипт `python3 script.py` изменит переменные родительского терминала**: дочерний процесс получает собственную копию окружения и не может менять память своего родителя (`bash`).
